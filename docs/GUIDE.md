# Project guide

How to operate `$DOMAIN` — the project's repository layout, deployment commands, protected host resources, per-service edit-safe facts, and operational gotchas. Read this before editing anything.

This guide is the only project-specific reference — architecture and design rationale included. The repo-page pitch lives in `README.md`; agent rules in `docs/AGENTS.md`; open problems in `docs/ISSUES.md`; the migration runbook in `docs/MIGRATE.md`.

## What runs here

One Debian VPS runs the lab in Docker Compose: the Caddy edge (`$DOMAIN`, host-network reverse proxy with per-vhost Let's Encrypt certs) plus the modules declared in `config/modules.conf` — one directory under `modules/`, one compose file, one vhost and one data dir each (Nextcloud stack with PostgreSQL/Redis/Talk HPB/coturn, Vaultwarden, Uptime Kuma, Docker Mailserver + Roundcube). Host services sit beside the containers — ttyd (web terminal), dnsmasq (tailnet DNS) and the goose agent (service table below).

**Which modules are actually installed is a runtime fact**, not a doc fact: `scripts/install/install.sh` writes `$DATA_DIR/installed-modules.conf` at the end of every run, and `make fetch` / `make fetch-more` / `make smoke` read it. A module that is **not installed** is ABSENT — no container, no data, no route (its vhost answers 502 if one is deployed). It is **not** "tailnet-only"; see "Module state vs route exposure" below.

The public hostnames (`cloud` `vault` `kuma` `mail` `talk` `www`) go through Cloudflare; `tail.$DOMAIN` is tailnet-only. A second tailnet-only VPS receives the nightly Nextcloud `pg_dump` (`/etc/cron.d/nc-storage`, installed by `scripts/ops/datadir-nfs.sh`, last 7 kept) and exports the NFS datadirectory that `make connect` (datadirectory) mounts at Nextcloud's `cloud/users` (see the `connect` row below). The authoritative hostname/module/container lists are the ones the scripts derive at runtime: `config/modules.conf`, `installed-modules.conf`, `docker ps` — never this sentence.

## Request flow

```
                   ┌─────────────────────────────────────────────┐
    Public DNS ──► │            Cloudflare (proxy)               │
                   │          cloud / vault / kuma / www         │
                   └──────────────┬──────────────────────────────┘
                                  │ HTTPS (LE cert via DNS-01)
                                  ▼
                           ┌──────────────┐
                           │    Caddy     │  port 80 → 308 redirect
                           │  ($DOMAIN)  │  port 443 (per-vhost LE)
                           └──────┬───────┘  custom image with the
                ┌─────────────────┼─────────────────┐     caddy-dns/
                │                 │                 │     cloudflare
                ▼                 ▼                 ▼     plugin
           reverse_proxy    reverse_proxy      php_fastcgi
           vaultwarden      uptime-kuma        nextcloud:9000
           (172.22.0.4:80)  (172.22.0.6:3001)  (Nextcloud FPM)
           (also:
            roundcube webmail 172.22.0.10:80 —
            mail platform Postfix/Dovecot at 172.22.0.9, ports 25/465/587/993)

    tail.$DOMAIN is tailnet-only (not in public DNS) — "/" serves
    the tailnet door list (this domain's tailnet-only routes: the
    shell plus one card per registered device session) and "/ttyd"
    opens the host terminal with NO second credential; non-tailnet
    sources get 403 before anything else runs.

                     ┌─────────────────────────────────────────────┐
                     │ Tailscale MagicDNS / split DNS              │
                     │ forwards tail.$DOMAIN queries to the VPS   │
                     │ resolver (bound to Tailscale IP only)       │
                     └──────────────┬──────────────────────────────┘
                                    │ UDP/TCP <tailnet IP>:53
                                    ▼
                             ┌──────────────┐
                             │   dnsmasq    │  host systemd service
                             │  (host)      │  (not a container)
                             │  - address=/tail.$DOMAIN/<tailnet IP>
                             │  - forward . 1.1.1.1 1.0.0.1 9.9.9.9
                             └──────────────┘
```

One host, two ingress paths. Cloudflare fronts the public hostnames — proxied (TLS terminates at the CF edge and is re-encrypted to the origin with the per-vhost LE cert): `cloud` `vault` `kuma` `www`; DNS-only (grey cloud — their traffic is not HTTP(S)): `mail` `talk`. A vhost another project installs into this edge (kefoMC's `mc`) follows the same rule. Caddy on the origin 308-redirects port 80 and terminates per-vhost HTTPS on 443. `tail.$DOMAIN` never enters public DNS: tailnet clients resolve it through the VPS dnsmasq (bound to the Tailscale IP only), and Caddy's `@not_tailnet` matcher 403s any other source — so the vhost is unreachable off the tailnet even with a forged Host header against the public IP.

## Domains and access model

| Hostname | Cloudflare mode | Reachable by | What you get there |
|----------|----------------|--------------|--------------------|
| cloud.$DOMAIN | proxied | anyone | Nextcloud |
| vault.$DOMAIN | proxied | anyone | Vaultwarden |
| kuma.$DOMAIN | proxied | anyone | Uptime Kuma |
| www.$DOMAIN | proxied | anyone | the `/download` drop folder + whatever pages the operator keeps in `$DATA_DIR/www` (the homepage redirect and any `/welcome*` tellings are instance content, not repo content) |
| mail.$DOMAIN | DNS-only | anyone | Roundcube webmail + SMTP/IMAP |
| talk.$DOMAIN | DNS-only | anyone | Talk signaling `/signaling` + TURN/STUN |
| tail.$DOMAIN | not in public DNS | tailnet only | the tailnet door list at `/` (this domain's tailnet-only routes only — fetched live, unauthenticated), ttyd at `/ttyd` (Tailscale membership only, no second credential), else `ok` |

Per-hostname operational detail lives in the service-reference bullets; the cross-cutting rules are that anything whose traffic is not HTTP(S) (mail, talk) must stay grey-cloud at Cloudflare, and the tailnet hostname never enters public DNS.

`tail.$DOMAIN` serves the tailnet door list at `/` — the domain's **tailnet-only** routes (the shell + one card per registered device session), rendered as links from `/targets.json` fetched live on every visit (unauthenticated, no session, no commands — the page holds nothing). `/ttyd` carries **no second credential**: Tailscale membership is the whole gate, exactly as the operator asked (HTTP basic auth was removed 2026-09-22). Nothing on the vhost is cacheable: `no-store, no-cache, must-revalidate, max-age=0` + `Pragma: no-cache` + `Expires: 0`, and the ETag/Last-Modified validators are stripped, so browsers re-fetch every asset on every request.

### Module state vs route exposure

Two orthogonal facts; conflating them produces wrong reports (it produced one on 2026-09-22: an uninstalled Vaultwarden was described as "tailnet-only").

| Axis | Values | Where the truth comes from |
|------|--------|----------------------------|
| **module state** | `installed` / `not installed` | `$DATA_DIR/installed-modules.conf` (written by the installer); `config/modules.conf` declares which modules exist |
| **route exposure** | `public` / `tailnet-only` | the vhost itself: `tail.$DOMAIN` (or anything not in public DNS) is tailnet-only; everything else the edge serves is public |

An **uninstalled module has no route at all** — no container, no vhost serving it, no DNS. `vault.$DOMAIN` answering 502 means *the vault module is not installed*, never "vault is tailnet-only". Tailnet-only describes a route that **exists** and is reachable only from the tailnet. `make fetch` prints `vault (not installed)` in words (never colour alone) and `make fetch-more` adds a `routes` row that classifies every deployed vhost — `public:` / `tailnet-only:` / a `!dead` line for a vhost whose module is not installed. Quote those words when reporting.

## Design rationale

Why the layout is the way it is, in one place. Where a choice already has a dedicated section or gotcha below, this section points there instead of restating it.

### Edge: Caddy over nginx / Traefik, Cloudflare in front

- The Caddyfile maps one vhost per file (`modules/caddy/vhosts/<host>.caddy`), each owning its own TLS block; ACME renewal is built in, and the `caddy-dns/cloudflare` plugin enables DNS-01 so certs issue whether or not port 80 reaches the origin. Certs persist in the bind-mounted `/data` dir, so container recreates don't restart the 90-day clock. HTTP/3 needs no extra config.
- Cloudflare in front hides the origin IP and adds DDoS protection, bot challenge and rate limiting at the edge.
- Trade-off: Cloudflare Bot Fight Mode challenges clients that can't run JS (curl, desktop sync). The fix is a per-hostname WAF rule skip for `cloud.$DOMAIN` — see the `cloud` rationale bullet.

### `tail.$DOMAIN`: why it never enters public DNS

- The admin hostname should be reachable only from the operator's devices; public DNS would hand every bot a port that isn't meant to be public.
- Tailscale split-DNS means the name resolves the moment a device joins the network — no port forwards, no firewall holes — and the vhost uses a normal LE cert, so tailnet clients get a clean handshake instead of a self-signed warning.
- The VPS also advertises exit-node routes; IPv4+IPv6 forwarding lives in `config/sysctl/99-kefo.conf` so tailnet devices can route their internet traffic through it.

### Mail: why Docker Mailserver

- One Postfix + Dovecot container (active monthly releases; DKIM/DMARC/fail2ban/Rspamd built in) plus the official Roundcube image — the lightest trusted option next to Mailu (~8 containers) and Mailcow (~12 containers, 6–8 GB RAM). TLS reuse, DNS-only records, quotas and spoof-proofing are in the `mail` bullet.

### dnsmasq: why on the host, bound to the Tailscale IP

- Tailscale split-DNS on the operator's devices forwards `tail.$DOMAIN` queries to a resolver on the VPS that answers that one name and forwards everything else; one small host dnsmasq file does both.
- On the host (not in Docker), DNS survives `docker stop`, image pulls and `systemctl restart docker` — the failure modes a container `restart: unless-stopped` policy cannot cover — with a `Restart=always` systemd unit as the only supervisor.
- dnsmasq binds port 53 only to the host's Tailscale IP, never `0.0.0.0`, so the VPS is not an open resolver. systemd-resolved could do the job, but binding it to `0.0.0.0:53` on the host would fight Docker's port mapping.

### The `net` bridge: why a user-defined external network

- Inter-container DNS needs a user-defined bridge network; Docker's embedded resolver (127.0.0.11) answers container names automatically, so no Consul or service registry is needed. One shared `172.22.0.0/16` network (`external: true`) is reused across every compose file so the pinned bridge IPs attach cleanly (creation and the pin list: see the note under the service table).

### Nextcloud stack: why PostgreSQL + Redis + self-hosted TURN

- PostgreSQL replaced the stock SQLite, whose file-level locking caused intermittent 504s under concurrent sync and made consistent backups hard. The data dir is portable so the DB can move to a bigger host if it ever outgrows this one (see "Nextcloud DB").
- Redis is a pure cache with no persistence (see the Redis gotcha).
- Talk calls run on the official Go signaling server (`talk-hpb`) plus a self-hosted coturn, so call media never touches a public STUN/TURN service (see "Talk stack").
- The whole stack is RAM-capped to the operator's 3 GB ceiling with per-container `mem_limit`/`memswap_limit`. The caps are ceilings, not allocations — idle stays low (a 2026-09-12 review tightened them toward realistic spikes: caddy edge 128m, vaultwarden 384m, roundcube 384m); `earlyoom` plus these walls keep a runaway process from ever reaching the host.
- The mail ecosystem is reciprocal: Nextcloud (Mail app, outbound SMTP, notifications) and Vaultwarden (verification/invite email) both send through the same local mailserver mailboxes over the bridge.

## Repository layout

Top-level dirs: `modules/` (one compose file per module), `config/` (catalogues + reference copies of host configs, restored by `make install-config` and rendered by `make render`), `docs/` (agent rules, this guide, issue tracker, debug + migration runbooks, setup reference), `recipes/` (Goose agent tasks) and `scripts/` (categorised — the list lives under "Everything about scripts" below). `ls` is the source of truth — what's described here is the intent, not the full inventory.

- `modules/<ctn>/docker-compose.yml` — one per running container. Compose files are the source of truth for images, env vars, ports, volumes, healthchecks, and logging.
- `config/` — the skeleton's catalogues (`config/modules.conf`, the token documentation `config/instance.defaults`) plus reference copies of host-level configs (goose systemd unit, SSH hardening, dnsmasq, ttyd, docker daemon, sysctl, logrotate, tmux) and the web templates in `config/www/`. Rendered by `make render`; restored to live paths by `make install-config`. For an offline copy of the whole tree, use `make bundle-config`.
- `docs/` — `AGENTS.md` (agent rules), `GUIDE.md` (this file), `ISSUES.md` (tracker), `DEBUG.md` (deep-scan / debug runbook), `MIGRATE.md` (runbook for moving to a new VPS; printed by `make migrate`), `REF.md` (the token/variable reference).
- `recipes/` — reusable Goose agent tasks (read-only inspection + reports), versioned with the scripts and docs they operate on. Run via the `make goose-*` recipes below.
- `scripts/ops/optimize.sh` — universal Debian-family VPS performance optimizer in install.sh/datadir-nfs.sh style (banner, zero prompts, unattended run, Enter-refresh error loop → SUCCESS only when green). Merges OPTIMIZE.md + the repo's tuned values + `make cleanup`'s apt/docker part; idempotent, `--dry-run`/`--verify`/`--yes`, backs up edits to `/root/optimize-backup-<ts>`; applied on this host — re-running is a no-op. **It installs only the performance helpers** (`tuned`, `irqbalance`, `earlyoom`) when missing; service software (`docker`, `dnsmasq`, …) is never installed, and steps for absent software are skipped instead of failing (see Operational gotchas).

## Deployment

Manual — no CI/CD, pushes to `main` trigger nothing. Use the `Makefile` recipes (canonical) rather than raw `docker compose`.

### First-time setup and migration

`scripts/install/install.sh` is the plug-and-play path: it prompts for the domain, Cloudflare API token, and Tailscale auth key, then runs unattended — host services, docker, tailscale, the full stack (Nextcloud app + PostgreSQL + Redis + Talk HPB/TURN, Caddy, `vaultwarden`, `uptimekuma`, Docker Mailserver + Roundcube), the Cloudflare A records, LE certs, and the Kuma admin account (passwords printed once in the final summary — nothing is written to disk). Fully autonomous: no manual confirmations block success — the only follow-ups are printed in the summary (Tailscale split-DNS, mailboxes, and swapping the login keypair the script mints when no key was supplied — `ssh_keys` no longer blocks a keyless first run). Prerequisites: the CF zone must exist (fail-fast check) and the printed GitHub pubkey must be added. `make migrate` prints the manual runbook (`docs/MIGRATE.md`).

`scripts/install/uninstall.sh` is the exact opposite, in the same style (banner, per-module prompts defaulting to keep, tagged errors with problem/hint, Enter-refresh re-checks, success block): the first prompt picks the scope — specific modules, the whole framework (every phase preselected; data prompts still default keep), or cancel. It takes the deployment apart module by module (containers down, `installed-modules.conf` refreshed after each removal), then optionally the edge, the host services (+ the stack's ufw rules — tailnet SSH always stays), the packages, the `root` user and the tailnet membership (always last, so the session survives). It never deletes operator data without an explicit per-category confirm — the storage VPS NFS export is untouched, period; sshd hardening is deliberately kept (removing it would re-enable password auth). Log: `$LOG_DIR/uninstall.log`; the scope is preselectable via `uninstall mode = modules|all` in `scripts/install/defaults/uninstall.conf` or the `UNINSTALL_MODE` env.

### CMD Sheet

`make help` prints the common daily recipes and `make help-more` the granular/technical ones — together they are the single source of truth for the command surface (rendered by `scripts/info/help.sh` in the same aligned colored style as the dashboard; this section used to duplicate them, a duplicate drifts). `make fetch` renders the AIO dashboard (`scripts/info/fetch.sh`: host perf, every declared module with `(not installed)` spelled out, git, units, failed units with targets, docker, tmux, backups, mail, tailnet — one aligned colored read). Raw `git`, `docker compose`, `docker exec`, `systemctl restart`, and `tar` are reserved for cases no recipe covers (one-off diagnostics the operator asked for, log/file inspection, ad-hoc reads).

**Recipe output is uniform** — every recipe speaks three lines: `info:  <what it did>` (completion), `warn:  <non-fatal issue>` and `error: <failure>` (recipe exits 1). All messages go through `scripts/lib/mklog`; usage mistakes print `error: usage: …` and exit 1. The raw tool output (occ, docker, DMS setup) stays unmodified where it is the result itself.

`make git-com MSG="…"` takes a single-sentence `MSG` only — embedded newlines break the `git commit -m` quoting (`unexpected EOF` before the commit lands) and embedded double quotes break the recipe's `$(MSG)` substitution (`[: too many arguments]`). If the message needs a quote mark, wrap the whole `MSG=` in single quotes — the shell does not interpolate inside single quotes, so the embedded `"` survives intact.

### Boot and recovery

`kefo-stack.service` (`config/systemd/kefo-stack.service`; installed and enabled by `make install-config`) is the boot guarantee: a `oneshot` unit that runs `scripts/stack/stack-up.sh` after `docker.service` and `network-online.target`. It closes the one gap `restart: unless-stopped` cannot — a container stopped *cleanly* by hand (`docker stop`, `make dok-stop-*`) never comes back on its own, while `up -d` starts it again.

`scripts/stack/stack-up.sh` is the single bring-up path and never acts blindly: it derives the deployed units from the live system (`docker ps -a` plus each compose file's declared container names), so an uninstalled module is never started and never gets empty data dirs created under it. Modes: `--update` (pull + force-recreate — what `make update` runs), `--check` (start only what is missing), `--validate` (edge config only, changes nothing). In every mode the **Caddy edge goes LAST**, behind `caddy adapt` validation against the real mounts and a `caddy:rollback` image tag, and a failed edge recreate reverts to the previous image automatically. A broken edge therefore can no longer stop the rest of the stack from coming up — which is exactly what made a failed `make update` an operator lockout.

A periodic repair pass is deliberately **not installed**: `scripts/stack/stack-up.sh --check` exists for a systemd timer (`OnUnitActiveSec=5min`) meant to restart anything that died cleanly between boots. To add it, ship `config/systemd/kefo-stack-health.service` + `.timer` running `stack-up.sh --check`, then `systemctl enable --now kefo-stack-health.timer`. Off by default because a supervisor that starts containers behind the operator's back is a bigger behavioural change than the boot guarantee.

## Goose recipes

`recipes/` holds reusable Goose agent tasks — each one a `version/title/description/instructions/extensions/parameters/prompt` YAML file that tells the agent what to inspect, which tools it may use, what inputs it accepts, and what report to produce. Every recipe is **read-only**: it inspects and reports, never mutates the host, and the operator applies changes after review (the same "read-only first" discipline as `docs/DEBUG.md`). The agent's own rules stay in `docs/AGENTS.md`; these recipes point at it and at this guide rather than restating them.

The `make goose-*` front doors wrap `goose run --recipe <name>` with the repo-local `GOOSE_RECIPE_PATH` (`recipes/`), so the recipes stay versioned with the scripts and docs they operate on:

- `make goose-recipes` — list them (`goose recipe list`).
- `make goose-audit [FOCUS=…]` — full read-only audit (security/reliability/ops/docs drift).
- `make goose-review MODULE=…` — review one module (`cloud|vault|mail|monitor|edge`).
- `make goose-troubleshoot SERVICE=…` — triage a failure via `docs/DEBUG.md`.
- `make goose-check-backups [FOCUS=…]`, `make goose-check-network [FOCUS=…]` — backup and ingress/mail reviews.
- `make goose-validate-installer [TARGET=…]` — lint/review script changes (`bash -n`, no apply).
- `make goose-audit-docs [SCOPE=…]` — find doc drift/stale/duplicate.
- `make goose-deploy-plan CHANGE=…` — produce a deployment/upgrade plan.

The command list is rendered by `scripts/info/help.sh` (the same source as `make help-more`); the recipe files themselves are the source of truth for what each task does. Multi-word parameter values (e.g. `CHANGE`) hit the same make limitation as `make git-com MSG=` — pass a single token through `make`, or invoke the recipe directly: `goose run --recipe deployment-plan --params "change=upgrade the Nextcloud image"`.

## Protected host resources

**Never delete or disable any of these without explicit operator approval.** Per `docs/AGENTS.md` safety rule 1, if a task seems to require removing any of them, stop and ask.

- `/etc/systemd/system/goose.service` — goose agent systemd unit (`enabled`, `Restart=always`). Its server secret lives in `/etc/goose/goose.env` (root:root 0640, outside the repo — the unit reads it via `EnvironmentFile=`).
- Credentials are never left in loose files: the Kuma admin hash lives in its database, service secrets in `modules/*/.env` + `/etc/goose/goose.env`, and generated passwords are printed once at creation (`make kuma-passwd`, `make mail-password`). Never commit or re-print an existing secret.
- `/etc/systemd/system/ttyd.service` — ttyd web-terminal unit (`enabled`, `Restart=always`). Binds `172.22.0.1:7681` only (host bridge IP), gated by the Caddy tailnet match and the UFW INPUT allow from `172.22.0.0/16`.
- `/etc/dnsmasq.d/10-tailnet.conf` and `/etc/systemd/system/dnsmasq.service.d/override.conf` — host DNS resolver + systemd drop-in (`Restart=always`). Binds the host's Tailscale IP on port 53 only.
- `$DATA_DIR/caddy_data/` — Caddy runtime data dir (LE certs under `caddy/acme/`, ACME account keys, OCSP staples) and the `CF_API_TOKEN` file used for per-vhost ACME DNS-01. The Caddy container bind-mounts this dir at `/data` so certs persist across container recreates. The `CF_API_TOKEN` file is created by the operator (see `docs/MIGRATE.md`); do not commit it.
- `$DATA_DIR/cloud/html/` and `$DATA_DIR/cloud/users/` — Nextcloud bind mounts (html root + datadirectory; both owned by uid 33 with a `.ncdata` marker in `users/`). After the datadirectory move, `cloud/users/` is an NFSv4 mount of the storage VPS (`/etc/fstab`, `nofail`, boot-race-hardened per the fstab options in `scripts/ops/datadir-nfs.sh`) — the live datadirectory lives on the 1 TB box, and the local copy is kept at `cloud/users.local-backup` until the operator deletes it (the script won't offer the delete until the copy is verified).
- `$DATA_DIR/pgdata/` — Nextcloud PostgreSQL data dir (bind-mounted into the `postgresql` container). This directory migrates to the operator's 1 TB VPS when it joins the tailnet (see "Nextcloud DB" below).
- `$DATA_DIR/talk/` — generated Talk configs: `server.conf` (signaling; 644 — the signaling container drops to uid 850 and must read it) and `turnserver.conf` (coturn; 600). Rendered by `make talk-gen` from `modules/nextcloud/talk/*.example`; contains the signaling + TURN secrets (do not commit — gitignored).
- `$DATA_DIR/download/` — file-browser drop folder, served read-only at `www.$DOMAIN/download` (Caddy bind mount `/download:ro`). Owned by `root`; anything dropped here is publicly readable.
- `$DATA_DIR/www/` — the web root for `www.$DOMAIN` and `tail.$DOMAIN` (Caddy bind mount `/etc/caddy/www:ro`). Operator-owned pages, the placeholder homepage the installer seeds once, and the GENERATED `targets.json` (`make tail-targets`). The repo ships no pages; only the tail door-list template is tracked (`config/www/tail.html`) and re-rendered into this dir on every `make render`.
- `$DATA_DIR/mailserver/` — mail platform data: `data/` (Maildirs), `state/`, `logs/`, `config/` (DMS config incl. DKIM keys), `roundcube/` (webmail sqlite). Owned 5000:5000 / 33:33 as noted in the compose file.
- `net` Docker network — user-defined bridge, `external: true`, subnet `172.22.0.0/16`. Reused by all inter-container services.
- SSH keys, Nextcloud data, Vaultwarden data, uploaded files — user-only (also `docs/AGENTS.md` safety rules 7 and 8).

## SSH access

SSH is restricted to the Tailscale network only — the public internet cannot reach port 22. Password auth is disabled; root login is key-only (`PermitRootLogin prohibit-password`); `AllowUsers root`. Config: `/etc/ssh/sshd_config.d/50-cloud-init.conf`. `root@$HOSTNAME` is the only entry point: the installer (`scripts/install/install.sh`) writes this file only when an operator key is already present in `/root/.ssh/authorized_keys` (so a keyless box is never locked out; instead it raises the `ssh_keys` tag and leaves password auth untouched until a key is added — never minting a server-side keypair). The storage VPS is reached as `root@<storage tailnet IP>`: `make connect` installs the operator's key there (passwordless) and root's key (used by the `pg_dump` cron).

The `net` Docker network is `external: true` — create once on a fresh host with `docker network create net --subnet=172.22.0.0/16` (the compose files pin `172.22.0.x` bridge IPs; a default-subnet network rejects them). All inter-container services use `expose`, not `ports`. The exception is `caddy`: it runs with `network_mode: host` so Caddy sees the real client source IP — without host networking, Docker DNAT rewrites every packet to `172.22.0.1` (the bridge gateway) before Caddy sees it, which breaks the `@not_tailnet` remote_ip matcher on `https://tail.$DOMAIN`. The host network namespace is on the `net` bridge at `172.22.0.0/16`, so Caddy still dials upstream containers by their bridge IP (see Caddyfile). dnsmasq binds to the Tailscale IP only, not `0.0.0.0`.

### Talk stack (Nextcloud Talk HPB + TURN)

**What it is, in plain language.** Nextcloud Talk = chat + audio/video calls. Calls are WebRTC: two browsers try to talk directly (peer-to-peer). Three helpers make that reliable:
1. **Signaling** (`talk-hpb`, the official Go server) — the "switchboard". Every Talk client keeps a websocket open to it (`wss://talk.$DOMAIN/signaling/spreed`); the signaling server tells participants who else is in the call and relays small control messages. Nothing about the call *media* flows through it.
2. **STUN** — "what's my public IP?" so two devices behind home NATs can find each other. coturn answers this on `talk.$DOMAIN:3478`.
3. **TURN** — when direct P2P fails (mobile CGNAT, hotel/corporate WiFi, firewalled networks), coturn *relays* the media between the two sides. Credentials are minted per-session by Nextcloud from a shared secret, so it is not an open relay. Both STUN and TURN live in the same coturn container (~9 MB RAM actual).

Nextcloud tells clients about the public endpoint (`https://talk.$DOMAIN/signaling`) — the only registered signaling entry (NC 34 deprecates multiple high-performance backends; the old internal `http://172.22.0.12:8080` registration was removed 2026-08-31). The signaling server reaches Nextcloud back via its own `[backend1] urls` (`extra_hosts` maps `cloud.$DOMAIN` → 172.22.0.1), so no internal URL registration is needed. The Caddy vhost strips the `/signaling` prefix before proxying — the signaling server serves its websocket at `/spreed` and its API at `/api/v1/*`.

`modules/nextcloud/docker-compose.yml` runs four containers: `nextcloud` (.5), `redis` (.11), `talk-hpb` (.12, strukturag/nextcloud-spreed-signaling — the official Go server, no NATS needed), `talk-relay` (.14). RAM hard caps sum to 2.02 GB with the DB (1g + 128m + 256m + 128m + 512m) — the operator's 3 GB ceiling. All four carry compose healthchecks (`docker ps` shows them `healthy`); talk-relay's is a real STUN binding probe via the image's `turnutils_stunclient` — a bare TCP connect would pass while the UDP/STUN path is broken.

- **Config generation** — `make talk-gen` (idempotent): writes missing secrets into `modules/nextcloud/.env` (`SIGNALING_SECRET`, `SIGNALING_HASH_KEY`, `SIGNALING_BLOCK_KEY`, `SIGNALING_INTERNAL_SECRET`, `TURN_SECRET`, `SMTP_PASSWORD`, plus `POSTGRES_*`/`REDIS_HOST`) and renders `$DATA_DIR/talk/{server.conf,turnserver.conf}` from the committed `modules/nextcloud/talk/*.example` templates. Run it once after a fresh clone/deploy before starting the stack.
- **Signaling registration in Nextcloud** — `occ talk:signaling:add` once, with the public URL (clients): `docker exec -u www-data nextcloud php occ talk:signaling:add https://talk.$DOMAIN/signaling <SIGNALING_SECRET>`. The `[backend1] secret` in `server.conf` must match. The `[backend1] urls` is the Nextcloud instance the signaling server calls back into (`https://cloud.$DOMAIN`). The internal `http://172.22.0.12:8080` entry was removed 2026-08-31 — NC 34 deprecates multiple HPBs.
- **TURN registration** — `occ talk:turn:add <schemes> <server> <protocols>` (protocols are positional — there are no `--udp`/`--tcp` options) with the same `--secret` as `turnserver.conf`'s `static-auth-secret`:
  `docker exec -u www-data nextcloud php occ talk:turn:add turn talk.$DOMAIN:3478 udp,tcp --secret <TURN_SECRET>`
  `docker exec -u www-data nextcloud php occ talk:turn:add turns talk.$DOMAIN:5349 tcp --secret <TURN_SECRET>`
- **talk.$DOMAIN** — the A record MUST be DNS-only at Cloudflare (grey cloud): TURN speaks UDP/TCP on 3478/5349 + relay 49160-49200, which the CF proxy can't carry. UFW opens those ports (`sudo ufw allow 3478/udp,tcp; 5349/tcp; 49160:49200/udp,tcp`). Caddy issues the talk.$DOMAIN LE cert via DNS-01 (needed by coturn for TURNS on 5349 — coturn mounts `caddy_data` at `/caddy:ro`); start coturn only after the cert exists. `make smoke` asserts the `/signaling` websocket answers (a bare `ok` stub fails it).

(`install.sh` does all of this automatically — including publishing the DKIM TXT — leaving only the PTR record provider-side.)
- **Talk rationale** — recording and SIP backends are intentionally unconfigured (no external recorder / SIP trunk); the HPB's "missing features: changed-users" notice is expected without federation and harmless.

Rewrites use that loop (same family as `scripts/ops/identity-rebuild.sh` (email swap) and `scripts/ops/drop-path.sh` (path purge, e.g. the 2026-09-03 `modules/nextcloud/.env` removal) — plumbing, parents-first, multi-root-safe). Verify after every run: identities uniform, tree of tip unchanged, messages + dates byte-identical, commit count preserved (1 root / 0 merges on the current history), `git fsck` clean. **No backup tags exist** — snapshots of pre-rewrite histories were destroyed 2026-09-03 (they held the scrubbed old identities + the `.env` secret) and the old two-root objects were pruned after the 2026-09-06 linearization; the $GITHUB_USER-era commits survive only inside `main` under the noreply identity (operator's explicit choice). Don't re-rewrite history to chase the graph — noreply commits are guaranteed-attributed; re-rewriting just risks re-triggering the index break.

## Generalization principle

Scripts and manifests stay **global** — they derive everything from the live system instead of hardcoding instance specifics (see `docs/AGENTS.md` rule 12). In practice here: install.sh/datadir-nfs.sh auto-detect container names, the datadirectory and DB credentials; user/group lists come from `occ`/`oc_users`, never a fixed roster; persistent recovery manifests are **generated** by `make nc-capture` into `cloud/recovery/` **outside the repo** (instance state, like `pgdata`/`backups` — never commit them; the appropriate command is `make nc-capture`, re-run to refresh). Before writing a specific user, host, IP, port, path, or container name into a script or doc, ask whether it can change — if it can, detect or prompt for it instead. Existing hardcoded leftovers should be migrated to this pattern when touched.

## Operational gotchas
- A deliberate `systemctl stop dnsmasq` takes all tailnet-side `*.$DOMAIN` resolution down. Restart with `make systemd-restart-dnsmasq`.
- **`systemctl restart ttyd` kills every shell it serves — including the agent that ran it (2026-09-11 19:58)** — ttyd spawns its shells (tmux sessions included) inside its own cgroup, so the restart SIGTERMs the whole group: the in-flight agent died mid-run and its tmux session vanished with it. `make install-ttyd` now refuses when the calling shell's `/proc/self/cgroup` sits inside `ttyd.service`; deploy ttyd config from SSH, or restart manually from a non-ttyd terminal.
- **Dovecot/postfix reject plaintext SMTP/IMAP auth** — Roundcube must use STARTTLS (`tls://mail.$DOMAIN:143` / `:587`). The env-derived `ROUNDCUBEMAIL_*` settings in the compose file cannot express the TLS prefix; the override lives in `modules/mailserver/roundcube-tls.inc.php` (included by the image entrypoint) and the compose `extra_hosts` maps the FQDN to the bridge IP.
- **Mail DNS records must stay DNS-only at Cloudflare** — MX and the `mail.$DOMAIN` A record are grey-clouded; a proxied record breaks SMTP/IMAP (CF only proxies HTTP(S)).
- **`talk.$DOMAIN` must also stay DNS-only at Cloudflare** — TURN relays media over UDP/TCP on 3478/5349 + 49160-49200, none of which the CF proxy carries. A proxied record breaks Talk calls (media can't reach coturn). The HTTPS/signaling side still works DNS-only (DNS-01 cert).
- **PTR is provider-side** — the IP has no PTR record (inbound 25 is now open), so outbound mail reputation with Gmail/Outlook is blocked until the operator sets reverse DNS at the provider (see `docs/ISSUES.md`).
- New `*.$DOMAIN` CF records can appear "down" on tailnet devices: dnsmasq negative-caches the NXDOMAIN if the hostname was queried before the record existed. After creating a CF record, restart dnsmasq (`make systemd-restart-dnsmasq`).
- The Makefile sets `SHELL := /bin/bash` explicitly. Without it, recipes run under `/bin/sh` (dash on Debian) and `set -eu` semantics differ — `dash` aborts on any unset variable reference, while `bash` only aborts on expansion failures. If you see `parameter not set` from a recipe, the Makefile shell setting is the first place to look.
- Cloudflare's free tier rate-limits rate-limit rules to a 10s min window. Plan ahead if a public endpoint ends up attracting more traffic than expected.
- **Every Caddy vhost has its own TLS block** — don't reintroduce a shared wildcard cert. The wildcard CF Origin cert at `$(REPO)/certs/` covered `*.$DOMAIN`, so a vhost without its own `tls` directive would pick up the wildcard as a SNI fallback and the per-vhost ACME automation policy would never fire. Lesson: a vhost with no `tls` directive appears to "use ACME by default" but actually picks up any loaded cert that matches the SNI.
- **Caddy stock `caddy:2.x` doesn't include `caddy-dns/cloudflare`** — needs a custom `xcaddy` build (see `modules/$DOMAIN/Dockerfile`). Also: `caddy-dns/cloudflare` v0.2.3 rejects the new 53-char CF token format with a generic "API token appears invalid" error during plugin provisioning — pull from `caddy-dns/cloudflare@a8737d0` (master) until a tagged release ships the regex fix.
- **`caddy:2.11.4` requires Go ≥ 1.25.1** to build — the `golang:1.25-bookworm` image satisfies this. Older builder images (e.g. `golang:1.24-bookworm`) fail with `go: github.com/caddyserver/caddy/v2@v2.11.4 requires go >= 1.25.1`. If you bump Caddy, check the new `go.mod` `go` directive and bump the builder image too.
- **`network_mode: host` is required for `@not_tailnet` to work.** Docker DNAT rewrites every packet to `172.22.0.1` (the bridge gateway) before Caddy sees it. Without `network_mode: host`, the `100.64.0.0/10` matcher matches nothing and every tailnet request gets 403. This is set in `modules/$DOMAIN/docker-compose.yml` — do not "fix" it.
- **`docker compose env_file:` reads the file as the UID running `make`, NOT as the UID inside the container** — compose parses `env_file:` at the host side. The `CF_API_TOKEN` file must be readable by the user running the compose command (`root`), mode 0644; chowning it to the container's uid (201) breaks the read and Caddy ends up with no token. The **directory** needs `+x` for `root` too: `caddy_data` is chowned `201:201` for the container, so `install.sh` sets it to `0711` — under the root umask's `0700` the compose read dies with `open …/caddy_data/CF_API_TOKEN: permission denied` *even though the file itself is `root`-owned 0644*, and Caddy never starts (which then cascades: no LE certs → mailserver restart-loops on its missing `mail.$DOMAIN` cert → DKIM keygen fails).
- **NFS needs the client package, not just the kernel module (lesson 2026-09-10)** — the NC host lists `nfs` in `/proc/filesystems` and loads the `nfs` module, so `mount -t nfs` *looks* mountable; without `nfs-common` there is no `/sbin/mount.nfs` helper and the kernel refuses with `fsconfig() failed: NFS: mount program didn't pass remote address`. The storage side (`nfs-kernel-server`, export, ufw 2049/111/20048) was never the fault. `scripts/ops/datadir-nfs.sh` now installs `nfs-common` on the NC host before mounting.
- **The NC host listens on `:111` (rpcbind), bound to `0.0.0.0`** — pulled in by `nfs-common` (the NFS *client* for the datadirectory) and socket-activated by systemd. It is not in the ufw allow list (default-deny applies), so it is not reachable off-host — a deep scan will surface it; do not "fix" it.
- **`scripts/ops/optimize.sh` bugs found live on the storage VPS (lesson 2026-09-10)** — (1) `append_lines()` re-appended the **whole** file before the new lines, so every call doubled the target: it duplicated `/etc/fstab` and `/etc/security/limits.conf`; the doubled fstab then made the noatime `sed` (a pattern built from file content) match nothing, so the remount "failed" and reverted — now only the missing lines are appended and the mount line is rewritten with `awk`. (2) re-checks assumed a full stack: `recheck limits` tested the current shell's `ulimit` (can't change until a new login → permanent false failure) and `recheck docker` ran `docker info` on a box without docker — now limits are checked via the config a new login reads, and absent software is skipped. `bash scripts/ops/optimize.sh --verify` is the way to prove a host is converged.
- **The datadirectory move keeps the rollback until the copy is verified (lesson 2026-09-10)** — over a DERP-relayed NFS link the migration's rsync stalled (34 MB of 197 MB copied) yet the old script still offered to delete `cloud/users.local-backup`; accepting it lost the datadirectory files (Nextcloud's skeleton content — recovered from `backups/cloud-backup-*`). The script now compares file counts before the delete prompt and skips that prompt whenever an error is pending; confirm the link is `direct` (`tailscale ping storage`) before migrating.
- **The NFS datadirectory mount must not race tailscaled at boot (lesson 2026-09-12)** — the fstab-generated mount unit started 1 s after `tailscaled` (netmap still loading, 0 peers), so the first TCP connect hung and systemd's default 90 s mount timeout killed the unit; `nofail` let the boot proceed and docker bind-mounted the *empty* local dir as NC's `/data` → Nextcloud 503s with `data directory is invalid`-class errors (kuma alerted). Recovery: `sudo systemctl start $(systemd-escape -p --suffix=mount "$DATA_DIR/cloud/users")` then `make dok-restart-nextcloud` — a bind mount made while the mount was down pins the placeholder dir until the container restarts. The fstab line (`scripts/ops/datadir-nfs.sh` `ensure_mount` writes it) now carries `x-systemd.after=tailscaled.service,x-systemd.mount-timeout=300s,x-systemd.before=docker.service` — ordered, 300 s budget, mounts before docker so containers never bind the placeholder; no `x-systemd.requires=` (it would propagate tailscaled restarts into unmounting the live datadir).
- **Spigot 1.8.8 on a modern JDK: strip the epoll natives or every connection dies (lesson 2026-09-12)** — Spigot 1.8.8 bundles Netty 4.0.23 (in `server.jar`, see `META-INF/io.netty.versions.properties`); its epoll transport reads via `io.netty.channel.epoll.Native` + `sun.misc.Unsafe`'s `Buffer.address`, which JDK 9+ module encapsulation breaks — every TCP/websocket connect throws `RuntimeException: Unable to access address of buffer` and resets. Symptoms that waste hours: the listener *injects successfully*, the server says `Done`, yet every HTTP/websocket probe gets "Connection reset by peer". Dead ends (all verified useless): `-Dio.netty.noUnsafe=true`, `-Dio.netty.noPreferDirect=true`, `--add-opens java.base/java.nio=ALL-UNNAMED`, `-Dio.netty.transport.noNative=true` (a Netty **4.1** property — 4.0's `Epoll.isAvailable()` has no gate, only "did the `.so` load"). Also: EaglerXServer needs Java 17 (class file 61) so Java 8 is not an option with the plugin. The fix: rebuild the jar without `META-INF/native/*.so` → `Epoll.isAvailable()` returns false → the server logs `Using default channel type` (NIO, heap-buffer path) and the eagler websocket handshake answers 101. The 07fd7727 template's install step does exactly this (`python3 zipfile` rewrite, `.nio-patched` marker).
- **`fs.protected_regular=2` silently blocks root writes in /tmp (lesson 2026-09-12)** — when a root-run script does `: > /tmp/file-owned-by-root` (O_CREAT on an existing file owned by another uid in a sticky world-writable dir), the kernel returns `Permission denied` **even for root**, with no log anywhere. It looks like an immutable file or a broken script; it's the kernel's symlink/hardlink-attack mitigation. Repro: `sudo : > /tmp/x` where x is root-owned. When testing scripts with temp files, either write to a non-sticky dir (`mkdir -p /tmp/subdir && chmod`), pre-chown the file, or expect EACCES on cross-uid creates in /tmp and /var/tmp.
- **A lingering test container can poison every later probe (lesson 2026-09-12)** — while iterating on a port-bound service, an earlier `timeout 150 docker run … --name <svc>-test` was still alive and holding the port; three "fix attempts" appeared to change nothing — because every probe hit the OLD broken container, and the new container's log showed `FAILED TO BIND: Address already in use` (easy to miss under a wall of startup output). Rule: before debugging a port-bound service, `docker ps -a` + `ss -tlnp | grep <port>` and remove every stale test container; treat "FAILED TO BIND" in the log as the primary signal, not the connect errors.
- **Bash array pitfalls that produced real uninstall.sh bugs (lesson 2026-09-12)** — (1) `arr=("${EMPTY[@]:-}")` with an empty array creates a **one-element array containing the empty string**, not an empty array — the loop body runs once with a bogus empty item (`bad array subscript` on an associative lookup). Use `arr=(); [ ${#SRC[@]} -gt 0 ] && arr=("${SRC[@]}")`. (2) Nested name construction `${RM_MOD_${k^^}:-false}` is a **bad substitution** in this bash — build the name first and use indirection: `v="RM_MOD_${k^^}"; [ "${!v}" = true ]`. Both compile fine under `bash -n`; they only explode at runtime — test with real data, not just syntax checks.
- **`scripts/ops/optimize.sh` applied here 2026-09-01** — fully automatic, **zero prompts** (every choice auto-detected or env-overridable). sysctl (BBR, buffers, dirty ratios, swappiness, `kernel.nmi_watchdog=0`, `sched_autogroup_enabled=0`, `vm.min_free_kbytes` = 1% of RAM computed live, `kernel.core_pattern=/dev/null`, THP=madvise incl. `defrag` via `/etc/tmpfiles.d/99-optimize.conf`), limits (nofile 65535 + `DefaultTasksMax=infinity`), journald caps, apt speed, **swap auto = RAM/3 rounded up, recreated only when the live size differs** (4G here — the host previously had **no active swap**), `noatime,nodiratime` auto on `/`, apt autoremove/clean + docker prune (make-cleanup style, no backup pruning), and **`tuned` (profile via `tuned-adm recommend`) + `irqbalance` + `earlyoom`** (the only packages the script installs — performance helpers; service software is never installed). **SSD/HDD auto-detect** (nvme name → ssd; `rotational=0` → ssd; discard support → ssd; else hdd): SSD gets fstrim, HDD gets SETRA. Here `vda` = rotational 1 + no discard → **hdd → SETRA 512 active** (256 kB readahead + `/etc/udev/rules.d/99-readahead.rules`), fstrim off. **tuned/sysctl cooperation**: tuned applies first, then `/etc/sysctl.d` overrides conflicting keys — that's tuned's own behavior (its sysctl plugin re-applies `sysctl --system` and defers to it, verified in `/var/log/tuned/tuned.log`); `tuned-adm verify` reports diffs on those keys **by design**. Opt out: `WITH_TUNED=0` / `WITH_IRQBALANCE=0` / `WITH_EARLYOOM=0` / `NOATIME=0` / `SWAP_GB=0` / `SETRA=0`. Backups under `/root/optimize-backup-*`; re-running is a no-op; `--verify` passes. Left by design: fstrim (disk detected hdd — `FORCE_FSTRIM=1` if SSD-backed VirtIO), service pruning (targets not installed). Requires root only — pure bash.
- **Two `$DOMAIN` containers (one named `<id>_$DOMAIN`) = a force-recreate that died mid-swap** — compose v5.5.0 creates the replacement under `<old-container-short-id>_$DOMAIN` and only frees the canonical name afterwards; if the run is interrupted between "create new" and "remove old" (e.g. Ctrl-C during the slow xcaddy rebuild), the next `up` starts both → two host-network Caddys on :80/:443 via SO_REUSEPORT sharing one cert store. Fix: `docker rm -f` the stale one, `docker rename` the survivor to `$DOMAIN`, then `make dok-recreate-$DOMAIN` + `make smoke`.
- **`make dok-recreate-$DOMAIN` (or `make dok-recreate-all`) takes ~3 minutes on a fresh VPS and prints zero progress** — `docker compose up --build` runs `docker build` in a streaming-tty mode that buffers until the step finishes. The build chain is `golang:1.25-bookworm` → `go install xcaddy` → `xcaddy build --with caddy-dns/cloudflare@a8737d0 v2.11.4` → `FROM caddy:2.11.4` + `COPY --from=builder`. `docker build --progress=plain` shows the steps.
- **The cert's issuer is the only reliable indicator of which path it took** — `curl -sk` returning 200 means "the listener responded", not "the right cert was served". Check `openssl x509 -noout -issuer` on a fresh `-no-keepalive` handshake. On CF-proxied hosts (every public vhost) the handshake sees Cloudflare's edge cert (issuer `Google Trust Services WE1`), not the origin's — check the origin cert with `openssl s_client -connect 127.0.0.1:443 -servername <host>` from the host instead (issuer should be `Let's Encrypt`).
- **One vhost's ACME order can stall behind Caddy's retry backoff (2026-09-22)** — on a fresh deploy every cert issued except `kuma.$DOMAIN`; `caddy validate` was fine and `/data/caddy/locks/issue_cert_kuma.{{DOMAIN}}.lock` kept getting touched while no cert dir appeared. Nothing surfaces because the global block sets `log { output file /dev/null }`; one `docker restart $DOMAIN` re-attempted the identifier and it issued in ~13 s. `install.sh`'s `issue_certs` now restarts Caddy once when any host is still pending after the poll. To read the ACME errors, temporarily set the global `log` output to `stderr` in `modules/$DOMAIN/Caddyfile` (bind-mounted, so a container restart picks it up), then restore it.
- **DMS `setup config dkim` exits 1 when the key already exists, and only `*.public.dns.txt` is publishable** — `docker exec mailserver setup config dkim domain $DOMAIN` returns 1 with "Not overwriting existing files", so judge success by the public key, not the exit code. The keys live in `mailserver/config/rspamd/dkim/` (`ENABLE_OPENDKIM=0`, Rspamd signs); `*.public.txt` is the BIND zone-file form with the key split across quoted lines, so grepping it for `p=…` publishes a truncated `mail._domainkey` TXT (~250 chars instead of ~390) — publish from `*.public.dns.txt`.
- **Host `ps` lists container processes** — `node server/server.js` (`docker-<id>.scope` = uptimekuma) and `supervisord` (= mailserver) are container processes visible in the host `/proc`, not stray host daemons. Check `/proc/<pid>/cgroup` (or `docker ps --no-trunc`) before calling a process unknown.
- **Host performance tuning** — network stack (`config/sysctl/99-kefo.conf`): BBR + `fq` qdisc, `tcp_fastopen=3`, `tcp_slow_start_after_idle=0`; Docker (`config/docker/daemon.json`): pull concurrency 10/10, `userland-proxy: false` (no compose publishes ports, so no behavior change); dnsmasq (`config/dnsmasq/10-tailnet.conf`): `cache-size=10000`.
- **Redis in the Nextcloud stack is a pure cache** — `--save "" --appendonly no`: no persistence, LRU at 128 MB. A redis restart drops locks + cache; Nextcloud reconnects on its own. The DB (Postgres) is the only durable state besides `/data`.

- **NC's system SMTP host must be the FQDN, not the bridge IP** — Symfony's SMTP client verifies the peer cert CN, so `mail_smtphost: 172.22.0.9` fails STARTTLS with `Peer certificate CN='mail.$DOMAIN' did not match expected CN='172.22.0.9'` and every mail (welcome emails, admin test mail) fails with "Email could not be sent". - **`make backup` artifacts are per-day, not per-run** — filenames carry only `YYYYMMDD` (hour dropped 2026-08-31), so a second `make backup` the same day overwrites/merges the same cloud/vault artifacts; `make clean-backups` still keeps the latest 3 per pattern.
- **Nextcloud background jobs run from the host cron** — `/etc/cron.d/nextcloud` (installed by `make install-cron`, part of `install-config`): `*/5 * * * * root docker exec -u www-data nextcloud php -f /var/www/html/cron.php`. The fpm image has no cron; without it, jobs run in Ajax mode (page-load only) and Talk/Mail/preview notifications stall. After install, set `occ background:cron`.

- **Recreating `mailserver` or `roundcube` breaks every active webmail session** — roundcube sessions are DB-backed (the UI keeps rendering "logged in") but the IMAP connection dies with the container, so users hit "Connection to IMAP server failed" until they log in again. Warn the operator before recreating either; the fix is a re-login, never a config change.
- **The edge guardrail** — app vhosts (cloud/vault/kuma/mail) must serve their real app: the pre-commit hook (installed via `make install-hooks`) blocks a bare `respond "ok"` in them (www and tail are exempt by design — www serves the operator's static pages, tail serves the tailnet home; a vhost another project installs, e.g. kefoMC's `mc`, is guarded by the pre-push smoke instead) and runs `caddy validate` on staged `modules/caddy/` changes; the pre-push hook runs `make smoke`. - **The data tree lives INSIDE the repo checkout — never `chown -R` the whole tree (lesson 2026-09-22)** — `$DATA_DIR` is `$REPO_DIR/data`, so a blanket `chown -R root:root $REPO_DIR` also seizes the container-owned data dirs (33 www-data, 70 postgres, 201 caddy, 5000 mailserver). Symptoms: Nextcloud answers 404 and `docker exec -u www-data nextcloud php occ` returns *"Could not open input file: occ"* (php-fpm cannot traverse its own document root); postfix answers `421 4.3.2 All server ports are busy` while its log shows `warning: cannot connect to service private/smtpd: Permission denied` (`/var/spool/postfix/private` lost its `postfix` ownership). - **`config/dnsmasq/10-tailnet.conf` carries a PLACEHOLDER address, never the live one (lesson 2026-09-22)** — the tracked file says `listen-address=100.64.0.1` (a CGNAT address that is nobody's node); `make install-config` / `make install-dnsmasq-conf` rewrite that literal to the live Tailscale IPv4 at deploy time, and `make backup` rewrites it back before pulling the file into the repo. The placeholder is a fixed literal on purpose (it used to come from a `TAILNET_SUBNET` instance value, which meant the tracked file contained a real address).
- **A module that is not installed has no route — never report it as "tailnet-only" (lesson 2026-09-22)** — `vault.$DOMAIN` answered 502 and the closing report called the vhost "tailnet-only"; the truth was that the `vault` module simply was not in `installed-modules.conf`. See "Module state vs route exposure".
- **The web root is INSTANCE DATA mounted inside the rendered config mount (2026-09-22)** — `modules/caddy/docker-compose.yml` mounts `${DATA_DIR}/www:/etc/caddy/www:ro` nested inside `${DATA_DIR}/rendered/caddy:/etc/caddy:ro`. Symptom if the mount is missing: every static page falls through to the `respond "ok"` stub.
- **An uninstalled module's own state is invisible to the edge (2026-09-22)** — `stack-up.sh` derives its unit list from the live containers, and the tail catalogue only lists routes that exist, so a module removed from `installed-modules.conf` neither starts nor appears anywhere. That is the designed behaviour; the only visible trace is the dead vhost line `make fetch-more` prints.

## Everything about scripts

**Where scripts live**: `scripts/`, one directory per category — `lib/` (shared, sourced: `instance.sh` for the instance values, `modules.sh` for module facts, `mklog` for recipe output), `install/` (installer, uninstaller, layout migration, `defaults/` prompt answer sheets), `render/` (`render.sh` + `render-all.sh`: skeleton → `$DATA_DIR/rendered` + the web root + the compose `.env` blocks), `stack/` (`stack-up.sh` bring-up, `smoke-vhosts.sh` live test), `modules/` (per-module helpers: Kuma users/import, mail+alias gen, talk-gen, nc-capture), `access/` (tail door-list generator, per-device ttyd sessions), `info/` (dashboard `fetch.sh`, deep dive `fetch-more.sh`, `help.sh`, goose token policy, gh-web-health) and `ops/` (connect, NFS datadirectory move, optimizer, identity rebuild, string/path helpers). `hooks/` holds the git hooks `make install-hooks` copies. `ls -R scripts/` is the source of truth. The Makefile is the canonical front door — `make <recipe>`; raw git/docker/systemctl belong to recipes.

**House style** (install.sh / datadir-nfs.sh / optimize.sh share it):
- Header comment block: what the script does, sources it merges, usage, env overrides.
- Banner (ASCII + description + warnings), then `ask_inputs()` at the very start only — prompts with defaults, each env-overridable; optimize.sh is zero-prompt (everything auto-detected).
- Fully unattended work after the prompts; every step idempotent; files backed up before edits (`/root/optimize-backup-<ts>`).
- Error framework: tagged errors via `fail()`; `problem()`/`hint()`/`recheck()` case-tables per tag; an Enter-refresh `resolve_errors()` loop at the end prints manual steps vs unexpected errors (problem + hint each), re-checks on every Enter, prints `✓ solved`, and only shows SUCCESS when the list is empty. Manual steps are items the operator must do (e.g. reboot); the loop cannot invent a success.
- mklog/recipe output is uniform: `info:` / `warn:` / `error:` (see CMD sheet).
- Rule 12 (stay global): scripts detect everything from the live system — container names, datadir, DB creds, disk type, swap state, services — never a hardcoded roster. Hardcoded values are promises the instance won't change.
- Dry-run / verify modes where a script mutates the host (`--dry-run`, `--verify`, `--yes`); run both before an apply.

**Doc-like checks when touching scripts**: after editing any script, walk every `.md` and grep the executable source for every concrete fact the docs claim (recipe names, paths, ports, hostnames) — drift/stale/duplicate rules apply to scripts↔docs exactly as to config↔docs (AGENTS.md doc-audit directives). Scripts that render configs from templates (`talk-gen`) keep the committed template as the single source; the rendered output is gitignored.

**Module awareness (`installed-modules.conf`)**: `scripts/install/install.sh` writes `$DATA_DIR/installed-modules.conf` at the end of every install run — one line per module actually installed (cloud/vault/mail/monitor; GENERATED, refreshed on re-run). `make smoke` reads it BEFORE checking anything and structures its sections per module: every check still runs and every FAIL still prints, but a failed section whose module is absent from the conf ends with one "module not installed — intended behaviour" note and those failures don't fail the exit code (per-section, not per-error). The edge (Caddy/www/tail) and host sections are core — always expected. A missing conf file means every module is expected (fail loud — fresh clones without an installer run). `make fetch` names the state on the modules row — `vault (not installed)` — in words, and `make fetch-more` adds the `routes` row (public / tailnet-only / `!dead` vhost with no installed module). The module roster itself comes from `config/modules.conf`, so adding a module is one line there plus a directory.

The **`games` module (PufferPanel + browser Minecraft) is not part of this repo** — it moved to its own project at `git@github.com:$GITHUB_USER/kefoMC.git` (see that repo's README). It plugs into this edge through the `net` docker network and a vhost file dropped into `modules/caddy/vhosts/`; the edge imports `vhosts/*.caddy`, so its presence is invisible to this repo.

**Debugging pointers**: `make fetch` (AIO dashboard), `make smoke` (live vhost/edge/host test — runs in pre-push), `make dok-logs-<ctn>` / `docker logs`, `journalctl -u <unit>`, `scripts/lib/mklog` for uniform messages. For a full deep scan or incident triage follow `docs/DEBUG.md`. When a script fails: reproduce with `--dry-run`/`--verify`, read the exact failing command's output, check the tag's `hint()`, and only then patch — then re-run the script end-to-end plus `make smoke` if the edge was touched.

### Operational gotchas

- **The edge must mount the RENDERED tree, not the tracked one (lesson 2026-09-22)** — `modules/caddy/docker-compose.yml` mounts `${DATA_DIR}/rendered/caddy`. Point it at `./` (the tracked dir) and Caddy does not error: the skeleton's site blocks literally say `https://www.{{DOMAIN}}`, so Caddy starts, binds 80/443, passes its `caddy version` healthcheck and serves **nothing** — every probe returns `000`, `curl -sk` gives no reply and `docker logs caddy` is empty. Symptom to grep for: edge healthy + every vhost `000`. Fix: `make render` then `make dok-recreate-caddy`; `scripts/stack/stack-up.sh` renders first in every mode and `--validate` catches a config that will not load.
- **Every log the project writes lives in `$LOG_DIR` (`/var/log/kefohaine`), one logrotate rule, nothing chronicle-style (2026-09-22)** — `install.log`, `uninstall.log` and any module log share the directory; the installer state is `$STATE_DIR`. Docker output is capped in `config/docker/daemon.json` (10m x3) and journald in the systemd drop-in. The pre-2026-09-22 paths (`/var/log/kefoserver-install.log`, `/var/log/homelab-install.log`) are relocated by `install.sh` on first run — never deleted.
- **`talk-hpb` needs `init: true` (2026-09-22)** — `strukturag/nextcloud-spreed-signaling` spawns short-lived `timeout` children and never reaps them: 81 zombies in ~40 minutes of uptime, which is PID-table exhaustion over weeks. `init: true` (tini as PID 1) fixed it; the count is 0. A `diagnose` pass that shows `N zombies` in `make fetch-more` is how it surfaced.
