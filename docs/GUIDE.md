# Project guide

How to operate `$DOMAIN` — the project's repository layout, deployment commands, protected host resources, per-service edit-safe facts, and operational gotchas. Read this before editing anything.

This guide is the only project-specific reference — architecture and design rationale included. The repo-page pitch lives in `README.md`; agent rules in `docs/AGENTS.md`; open problems in `docs/ISSUES.md`; the migration runbook in `docs/MIGRATE.md`.

## What runs here

One Debian machine runs the lab in Docker Compose: the Caddy edge (`$DOMAIN`, host-network reverse proxy with per-vhost Let's Encrypt certs — `tail.$DOMAIN` excepted, it uses Caddy's own local CA) plus the modules declared in `config/modules.conf` — one directory under `modules/`, one compose file, one vhost and one data dir each (Nextcloud stack with PostgreSQL/Redis/Talk HPB/coturn, Vaultwarden, Uptime Kuma, Mailu + Roundcube). Host services sit beside the containers — ttyd (web terminal), dnsmasq (tailnet DNS) and the goose agent (service table below).

**Which modules are actually installed is a runtime fact**, not a doc fact: the installer — the SOLE writer of `$DATA_DIR/wizard.state` — records the `enabled_modules` and sets the `finished` checkpoint **only when a run reaches success** (a failed or unfinished run leaves a non-finished state), and `make fetch` / `make fetch-more` / `make smoke` read it (through `scripts/lib/modules.sh`, the one accessor). A module that is **not installed** is ABSENT — no container, no data, no route (its vhost answers 502 if one is deployed). It is **not** "tailnet-only"; see "Module state vs route exposure" below.

The public hostnames (`cloud` `vault` `kuma` `mail` `talk` `www`) go through Cloudflare; `tail.$DOMAIN` is tailnet-only. A second tailnet-only machine can be made the PERMANENT live Nextcloud datadirectory host by `make nc-datadir-nfs` (`scripts/ops/nc-datadir-nfs.sh` — `export` moves this host's datadirectory over NFS to it; `import` restores this host's own previously-exported datadir); `make backup` ships ALL modules (not one at a time) to a tailnet device in one of two modes — bundles (`nextcloud-backup-*.tar.gz` = PostgreSQL DB + Nextcloud datadir, `other-backup-*.tar.gz` = vault/mailserver/kuma datadirs) or raw datadirectories (`nextcloud-*/`, `others-*/`); `make import-backups` previews what's available and asks for a typed yes before restoring. The database always stays on the main machine (see the `nc-datadir-nfs` row below). The authoritative hostname/module/container lists are the ones the scripts derive at runtime: `config/modules.conf`, `wizard.state`, `docker ps` — never this sentence.

## Request flow

```
                   ┌─────────────────────────────────────────────┐
    Public DNS ──► │            Cloudflare (proxy)               │
                   │          cloud / vault / kuma / www         │
                   └──────────────┬──────────────────────────────┘
                                  │ HTTPS (LE cert via DNS-01)
                                  ▼
                           ┌──────────────┐
                           │    Caddy     │  port 80 → 308 redirect
                           │  ($DOMAIN)  │  port 443 (per-vhost LE)
                           └──────┬───────┘  custom image with the
                ┌─────────────────┼─────────────────┐     caddy-dns/
                │                 │                 │     cloudflare
                ▼                 ▼                 ▼     plugin
           reverse_proxy    reverse_proxy      php_fastcgi
           vaultwarden      uptime-kuma        nextcloud:9000
           (172.22.0.4:80)  (172.22.0.6:3001)  (Nextcloud FPM)
           (also:
            roundcube webmail 172.22.0.10:80 (cube.$DOMAIN) —
            mail platform Postfix/Dovecot at 172.22.0.9, ports 25/465/587/993
            (mail.$DOMAIN: platform door + admin UI at /admin))

    tail.$DOMAIN is tailnet-only (not in public DNS) — "/" serves
    the tailnet door list (this domain's tailnet-only routes: the
    shell plus one card per registered device session) and "/ttyd"
    opens the host terminal with NO second credential; non-tailnet
    sources get 403 before anything else runs.

                     ┌─────────────────────────────────────────────┐
                     │ Tailscale MagicDNS / split DNS              │
                     │ forwards tail.$DOMAIN queries to the machine   │
                     │ resolver (bound to Tailscale IP only)       │
                     └──────────────┬──────────────────────────────┘
                                    │ UDP/TCP <tailnet IP>:53
                                    ▼
                             ┌──────────────┐
                             │   dnsmasq    │  host systemd service
                             │  (host)      │  (not a container)
                             │  - address=/tail.$DOMAIN/<tailnet IP>
                             │  - forward . 1.1.1.1 1.0.0.1 9.9.9.9
                             └──────────────┘
```

One host, two ingress paths. Cloudflare fronts the public hostnames — proxied (TLS terminates at the CF edge and is re-encrypted to the origin with the per-vhost LE cert): `cloud` `vault` `kuma` `www`; DNS-only (grey cloud — their traffic is not HTTP(S)): `mail` `talk`. A vhost another project installs into this edge follows the same rule. Caddy on the origin 308-redirects port 80 and terminates per-vhost HTTPS on 443. `tail.$DOMAIN` never enters public DNS: tailnet clients resolve it through the machine dnsmasq (bound to the Tailscale IP only), and Caddy's `@not_tailnet` matcher 403s any other source — so the vhost is unreachable off the tailnet even with a forged Host header against the public IP.

## Domains and access model

| Hostname | Cloudflare mode | Reachable by | What you get there |
|----------|----------------|--------------|--------------------|
| cloud.$DOMAIN | proxied | anyone | Nextcloud |
| vault.$DOMAIN | proxied | anyone | Vaultwarden |
| kuma.$DOMAIN | proxied | anyone | Uptime Kuma |
| www.$DOMAIN | proxied | anyone | the `/download` drop folder + whatever pages the operator keeps in `$DATA_DIR/www` (the homepage redirect and any `/welcome*` tellings are instance content, not repo content) |
| mail.$DOMAIN | DNS-only | anyone | Mailu platform door (admin UI at `/admin`) + SMTP/IMAP |
| cube.$DOMAIN | proxied | anyone | Roundcube webmail |
| talk.$DOMAIN | DNS-only | anyone | Talk signaling `/signaling/spreed` + TURN/STUN |
| tail.$DOMAIN | not in public DNS | tailnet only | the tailnet door list at `/` (this domain's tailnet-only routes only — fetched live, unauthenticated), ttyd at `/ttyd` (Tailscale membership only, no second credential), else `ok` |

Per-hostname operational detail lives in the service-reference bullets; the cross-cutting rules are that anything whose traffic is not HTTP(S) (mail, talk) must stay grey-cloud at Cloudflare, and the tailnet hostname never enters public DNS.

`tail.$DOMAIN` serves the tailnet door list at `/` — the domain's **tailnet-only** routes (the shell + one card per registered device session), rendered as links from `/targets.json` fetched live on every visit (unauthenticated, no session, no commands — the page holds nothing). `/ttyd` carries **no second credential**: Tailscale membership is the whole gate, exactly as the operator asked (HTTP basic auth was removed 2026-09-22). Nothing on the vhost is cacheable: `no-store, no-cache, must-revalidate, max-age=0` + `Pragma: no-cache` + `Expires: 0`, and the ETag/Last-Modified validators are stripped, so browsers re-fetch every asset on every request.

### Module state vs route exposure

Two orthogonal facts; conflating them produces wrong reports (it produced one on 2026-09-22: an uninstalled Vaultwarden was described as "tailnet-only").

| Axis | Values | Where the truth comes from |
|------|--------|----------------------------|
| **module state** | `installed` / `not installed` | `enabled_modules` in `$DATA_DIR/wizard.state` (written by the installer); `config/modules.conf` declares which modules exist |
| **route exposure** | `public` / `tailnet-only` | the vhost itself: `tail.$DOMAIN` (or anything not in public DNS) is tailnet-only; everything else the edge serves is public |

An **uninstalled module has no route at all** — no container, no vhost serving it, no DNS. `vault.$DOMAIN` answering 502 means *the vault module is not installed*, never "vault is tailnet-only". Tailnet-only describes a route that **exists** and is reachable only from the tailnet. `make fetch` prints `vault (not installed)` in words (never colour alone) and `make fetch-more` adds a `routes` row that classifies every deployed vhost — `public:` / `tailnet-only:` / a `!dead` line for a vhost whose module is not installed. Quote those words when reporting.

## Design rationale

Why the layout is the way it is, in one place. Where a choice already has a dedicated section or gotcha below, this section points there instead of restating it.

### Edge: Caddy over nginx / Traefik, Cloudflare in front

- The Caddyfile maps one vhost per file (`modules/caddy/vhosts/<host>.caddy`), each owning its own TLS block; ACME renewal is built in, and the `caddy-dns/cloudflare` plugin enables DNS-01 so certs issue whether or not port 80 reaches the origin. Certs persist in the bind-mounted `/data` dir, so container recreates don't restart the 90-day clock. HTTP/3 needs no extra config.
- Cloudflare in front hides the origin IP and adds DDoS protection, bot challenge and rate limiting at the edge.
- Trade-off: Cloudflare Bot Fight Mode challenges clients that can't run JS (curl, desktop sync). The fix is a per-hostname WAF rule skip for `cloud.$DOMAIN` — see the `cloud` rationale bullet.

### `tail.$DOMAIN`: why it never enters public DNS

- The admin hostname should be reachable only from the operator's devices; public DNS would hand every bot a port that isn't meant to be public.
- Tailscale split-DNS means the name resolves the moment a device joins the network — no port forwards, no firewall holes. The vhost uses Caddy's `tls internal` (its local CA), never Let's Encrypt: the name is never a public ACME identifier, so there is no order to rate-limit or renew, and browsers show a one-time warning for the untrusted CA — expected, and the cost of keeping the door self-contained.
- The machine also advertises exit-node routes; IPv4+IPv6 forwarding lives in `config/sysctl/99-kefo.conf` so tailnet devices can route their internet traffic through it.

### Mail: why Mailu

- One Postfix + Dovecot container (active monthly releases; DKIM/DMARC/fail2ban/Rspamd built in) plus the official Roundcube image — the lightest trusted option next to Mailu (~8 containers) and Mailcow (~12 containers, 6–8 GB RAM). TLS reuse, DNS-only records, quotas and spoof-proofing are in the `mail` bullet.

### dnsmasq: why on the host, bound to the Tailscale IP

- Tailscale split-DNS on the operator's devices forwards `tail.$DOMAIN` queries to a resolver on the machine that answers that one name and forwards everything else; one small host dnsmasq file does both.
- On the host (not in Docker), DNS survives `docker stop`, image pulls and `systemctl restart docker` — the failure modes a container `restart: unless-stopped` policy cannot cover — with a `Restart=always` systemd unit as the only supervisor.
- dnsmasq binds port 53 only to the host's Tailscale IP, never `0.0.0.0`, so the machine is not an open resolver. systemd-resolved could do the job, but binding it to `0.0.0.0:53` on the host would fight Docker's port mapping.

### The `net` bridge: why a user-defined external network

- Inter-container DNS needs a user-defined bridge network; Docker's embedded resolver (127.0.0.11) answers container names automatically, so no Consul or service registry is needed. One shared `172.22.0.0/16` network (`external: true`) is reused across every compose file so the pinned bridge IPs attach cleanly (creation and the pin list: see the note under the service table).

### Nextcloud stack: why PostgreSQL + Redis + self-hosted TURN

- PostgreSQL replaced the stock SQLite, whose file-level locking caused intermittent 504s under concurrent sync and made consistent backups hard. The data dir is portable so the DB can move to a bigger host if it ever outgrows this one (see "Nextcloud DB").
- Redis is a pure cache with no persistence (see the Redis gotcha).
- Talk calls run on the official Go signaling server (`talk-hpb`) plus a self-hosted coturn, so call media never touches a public STUN/TURN service (see "Talk stack").
- The whole stack is RAM-capped to the operator's 3 GB ceiling with per-container `mem_limit`/`memswap_limit`. The caps are ceilings, not allocations — idle stays low (a 2026-09-12 review tightened them toward realistic spikes: caddy edge 128m, vaultwarden 384m, roundcube 384m); `earlyoom` plus these walls keep a runaway process from ever reaching the host.
- The mail ecosystem is reciprocal: Nextcloud (Mail app, outbound SMTP, notifications) and Vaultwarden (verification/invite email) both send through the same local mailserver mailboxes over the bridge.

## Repository layout

Top-level dirs: `modules/` (one compose file per module), `config/` (catalogues + reference copies of host configs, restored by `make install-config` and rendered by `make render`), `docs/` (agent rules, this guide, issue tracker, debug + migration runbooks, setup reference), `recipes/` (Goose agent tasks) and `scripts/` (categorised — the list lives under "Everything about scripts" below). `ls` is the source of truth — what's described here is the intent, not the full inventory.

- `modules/<ctn>/docker-compose.yml` — one per running container. Compose files are the source of truth for images, env vars, ports, volumes, healthchecks, and logging.
- `config/` — the skeleton's catalogues (`config/modules.conf`, the token documentation `config/instance.defaults`) plus reference copies of host-level configs (goose systemd unit, SSH hardening, dnsmasq, ttyd, docker daemon, sysctl, logrotate, tmux) and the web templates in `config/www/`. Rendered by `make render`; restored to live paths by `make install-config`. 
- `docs/` — `AGENTS.md` (agent rules), `GUIDE.md` (this file), `ISSUES.md` (tracker), `DEBUG.md` (deep-scan / debug runbook), `MIGRATE.md` (runbook for moving to a new machine; printed by `make migrate`), `SKELETON.md` (the skeleton: tokens, values and rendering).
- `recipes/` — reusable Goose agent tasks (read-only inspection + reports), versioned with the scripts and docs they operate on. Run via the `make goose-*` recipes below.
- `scripts/ops/optimize.sh` — universal Debian-family machine performance optimizer in the installer/nc-datadir-nfs.sh style (banner, zero prompts, unattended run, Enter-refresh error loop → SUCCESS only when green). Merges OPTIMIZE.md + the repo's tuned values + apt autoremove/clean + docker prune (the retired `make cleanup` payload, minus backup pruning); idempotent, `--dry-run`/`--verify`/`--yes`, backs up edits to `/root/optimize-backup-<ts>`; also disables the same distro units the installer does (`cups`, `ModemManager`, `avahi`, `bluetooth`, `wpa_supplicant`, `openipmi`, `systemd-networkd-wait-online`, …); applied on this host — re-running is a no-op. **It installs only the performance helpers** (`tuned`, `irqbalance`, `earlyoom`) when missing; service software (`docker`, `dnsmasq`, …) is never installed, and steps for absent software are skipped instead of failing (see Operational gotchas).

## Deployment

Manual — no CI/CD, pushes to `main` trigger nothing. Use the `Makefile` recipes (canonical) rather than raw `docker compose`.

### First-time setup and migration

The installation wizard is the plug-and-play path. It opens with the ASCII banner, a WELCOME line and three WARN lines (unfinished-install warning, tailnet-only SSH, the log path), then asks `Do you wish to continue?` (and, on a box that already has a finished install, prints `[WARN] kefoCloud is already installed` and asks whether to repair it, with an orange `[WARN]` prompt tag rather than the usual grey `[INFO]`) — a `no` aborts and logs the refusal before anything changes. It then collects EVERY input up front, before any install work, in a fixed order, and persists each answer immediately (so an aborted run can be resumed): (1) apply-previous-answers (asked only when `wizard.state`/`instance.conf` exists), (2) locale country (resolved to an IANA timezone from the system `zoneinfo` and applied at once, so the checklist and message timestamps are in the operator's local time), (3) `Are you a collaborator of $REPO_NAME?` — when yes, its sub-prompts add one REQUIRED `name email` commit-identity line (spaces tolerated; re-asked until a valid pair; no blank skip, no fallback), then (only while the key is still unauthorized) the `Github SSH Key Prompt` section prints the public key to paste, verified automatically by polling `ssh -T` until GitHub accepts it (no manual re-check step, and no section at all once the key is authorized — e.g. on a resume) — (4) the device's public SSH key (required, strict: re-asks until a valid `.pub` line, installs it into `/root/.ssh/authorized_keys`; the key is saved in `wizard.state` so a resume reuses it and a fresh/no-resume run asks for it again), (5) Tailscale auth key, (6) Cloudflare API token (both echoed as typed — not hidden), (7) domain, (8) modules as ONE space-separated line (`cloud mail vault monitor`; any order, names not listed are off). Every affirmation accepts **only the words `yes`/`no`** — no shortcut, no default — and the answer is recorded as the boolean `true`/`false`. It then runs unattended: host services, docker, tailscale, the full stack (Nextcloud app + PostgreSQL + Redis + Talk HPB/TURN, Caddy, `vaultwarden`, `uptimekuma`, Mailu + Roundcube), the Cloudflare A records, LE certs for the public vhosts, and the Kuma admin account (passwords printed once — nothing written to disk; the Vaultwarden default account's master password is stored per key in the gitignored `modules/vaultwarden/.env`, like the Nextcloud admin, so a re-run prints the same one). Module credentials and secrets — the Nextcloud admin, the Vaultwarden SMTP sender and admin, `make talk-gen`, each module's `.env` → `seed_stack` — are seeded only when that module is on; a module the operator leaves off gets no creds and no sender mailbox minted for it. It writes its state to `$DATA_DIR/wizard.state` (mode 0600; enabled modules + the `finished` checkpoint + the prompted secrets) and is its **sole writer**. When the GitHub opt-in is yes it mints `/root/.ssh/github_key` (the only keypair the installer creates) and prints the public key to paste into GitHub; once the key is authorized it also points `origin` at `git@github.com:$GITHUB_USER/$REPO_NAME.git` (so an operator `git push` needs no GitHub login), and the push is attempted LAST, to a one-shot `temppush` URL remote — a non-collaborator's push is rejected by GitHub (the push **is** the collaborator check, reported as an error). When the opt-in is yes the push is **mandatory**: a push that cannot run (unauthorized key, missing identity) or is rejected (non-collaborator, diverged history) flips the run to `finished=false` and suppresses the success block. The run ends with the checkpoint sequence: the GitHub `--no-verify` push (a rejected push means not finished, so no checkpoint is opened) → `write_state` (`finished=true`) → ONE `make smoke` (which aborts unless `finished=true`; no bypass) whose exit code is the verdict → on failure the installer writes `finished=false` and stops with no success prompt → otherwise the success block → the yes/no offer to run `scripts/ops/optimize.sh`. `make smoke` never writes state: it reports, and the installer — its sole writer — records the verdict of the single call it makes, so an operator's own `make smoke` and the pre-push hook can only report. Two output channels: `$LOG` gets EVERYTHING (every step, command, decision and the full output of anything redirected into it), the console gets only what a human watching the run needs — the banner, the consent/answer prompts, the live task checklist and the final summary. `wizard.log` is TRUNCATED at the start of every run, so one file describes exactly one run. `log()`/`detail()` are log-only (timestamped, never colored in the file); `msg()` prints the timestamped line to the console AND appends a plain copy to `$LOG` (escapes never reach the file), and is MUTED while a task runs so nothing splits the checklist. After a grey `[INFO]`, purple `[HH:MM:SS]` and a white verb line that names the run — `Installing..` or `Repairing..`, the run shows ONE fixed task checklist (`[H] System Packages`, `[H] SSH Hardening`, `[H] Firewall Rules`, `[H] Tailscale Connectivity`, `[H] Docker Engine`, `[H] Goose CLI`, `[H] Repository Setup`, `[H] Host Services`, `[H] DNS Records`, `[H] Repo Hygiene`, `[S] Stack Config`, `[S] Containers Up`, `[S] SSL Certificates`, `[S] Mail Setup`, `[S] Nextcloud Setup`, `[S] Vaultwarden Setup`, `[S] Monitoring Setup`, `[B] Smoke Pass` (grouped host → stack → both; the tag is coloured — `[H]` host purple, `[S]` stack orange, `[B]` both green, brackets included — and is never rewritten; a skipped row says `[SKIP]` in the status column and keeps its `[H]`/`[S]`/`[B]` tag — nothing else is appended to the row — marked `[SKIP]` — with its `[HH:MM:SS]` stamped at the same moment — from the moment the block is drawn, i.e. before the pipeline reaches the row, not when it walks past it): each row prints its STATUS bracket FIRST, then the task's time column — `[HH:MM:SS]` in purple once it is done, or (while running, TTY only) the moving orange marker ping-ponging inside the same purple brackets — the operator's currency sign, resolved from the locale country (falling back to `$` when that country has no single-column sign), a silent cosmetic choice — then the task name (`[DONE] [04:11:42] Repository Setup`, `[EXEC] [€       ] Repository Setup`); a piped run prints each row once, when it finishes. Each row starts grey `[WAIT]` — its time column shows the `[--:--:--]` placeholder until the row ends, then the real `[HH:MM:SS]` —, the running row is orange `[EXEC]`, a finished row green `[DONE]`, a module that is off orange `[SKIP]` (its own marker, not `[DONE]`) or, on failure, red `[FAIL]` — a failed task PAUSES the run on its `[FAIL]` row (later rows stay `[WAIT]`) and prints the error below the list; once the operator resolves it (press `Enter` after fixing), that block is wiped, the row flips to `[DONE]` and the run continues from the next task, but a failure that stays unresolved — or a run with no terminal to re-check on — HARD-STOPS the installer: the tasks after it are left `[WAIT]`, the run is recorded `finished=false`, and it is never run on past the failure and marked `[DONE]`. The success block that closes a green run lists only the enabled modules' sites (Nextcloud / Vaultwarden / Uptime Kuma / Webmail) plus the always-present `Shell` (tailnet) line and the machine's addresses, so a module that is off is never advertised. An inline `[FAIL]`/prompt block (the resolve prompt, the Nextcloud apps plan/confirm) is transient: it is counted and cleared off the screen when it is done, leaving the to-do list. The checklist uses relative cursor moves only (no DECSC/DECRC, which some terminals ignore); it counts the PHYSICAL rows printed below the block (`_TAIL`, terminal width from `stty size`, so a wrapped note counts its full height) and starts every block/note write with an explicit CR (so a terminal without ONLCR cannot concatenate rows) so every redraw returns to the block no matter what a task printed, and while an interactive prompt owns the tty the animator pauses, then resumes by clearing everything printed below and redrawing the running row — so a prompt's app list/prompt vanishes and the checklist resumes on its own row instead of appending a duplicate. Console timestamps are purple (`[HH:MM:SS]`, plain when not a TTY or `NO_COLOR` is set). No time *estimates* anywhere. The only prompts after the up-front block are state-dependent decisions that cannot precede the state they read: the Nextcloud app-action confirm/proceed/drop/resolve, the resolve-errors re-check, and the optional optimize. Resume semantics are strict: **yes** reuses every saved value and asks only the missing ones; **no** ignores the previous answers and re-asks everything but does **not** delete them. A resume re-runs the WHOLE pipeline (it is not a skip — the installer is idempotent, so every step is safe to repeat: containers are recreated, DNS records upserted, setup steps re-applied); when the prior run recorded `finished=true` the installer says so before starting. Repair mode is fully idempotent and add-only: it never tears down the stack (the only hand-off is `uninstall.sh --granular` for a module the operator turned OFF, which removes just that module), skips services whose inputs hash unchanged, recreates Caddy only when the rendered config is newer than the running container, and never re-issues an already-issued certificate: hosts that already serve a cert are skipped entirely (`cert_issuer_now()` single-shot check) — no trigger request, no ACME order — and one issuance attempt per provider per run is the ceiling, so a rate-limited run is waited out, not retried; Mailu's cert is only re-copied and `mailu-front` only restarted when the cert bytes actually changed. `task_ssh` applies sshd hardening in the same run (the box is key-only; the installer never mints a server-side *login* key). Non-root login accounts are removed and the machine is renamed — this is the ONLY tracked file that names the machine (`NODE_NAME="kefomachine"` at the top, the explicit exception to "derive everything"), and the Tailscale node adopts the OS hostname so no `--hostname` flag is passed. Prerequisites: the CF zone must exist (fail-fast). The repo owner (`{{GITHUB_USER}}`, used for the rendered vhosts and the `origin` remote) is never prompted — it is read from the checkout's own `origin`. `make migrate` prints the manual runbook (`docs/MIGRATE.md`).

The cloud module is config-driven for app choices: the operator edits `config/cloud/apps.conf` (optional and EMPTY — this file is untracked/gitignored, so it is operator config: editing it can never alter the repo; verbs `install&enable=`, `install&disable=`, `disable=`, `remove=`, one action per line, multi-action lines supported; read on a FRESH install only — on a resume the selection is already in the instance), and the installer prints the exact planned actions and asks for a single confirmation — that is the only app-related prompt, and it appears only for the cloud module, and only when the operator's own config has actionable lines. Two apps are ENFORCED in code and are never configurable, never listed in the plan and never asked: `spreed` (install&enable — Talk's signaling backend) and `app_api` (install&disable — it opens an app-install path from the web UI). They are applied silently and recorded in `wizard.log` only; a `spreed`/`app_api` line in `apps.conf` is dropped with an `ENFORCED` note, and changing them is done from the instance's own Nextcloud Apps page. The config is the intent: a `disable=` on an installed app is applied without prompting, and a satisfied action is skipped silently; only a genuine config/live-state surprise prompts — `disable=` on a NOT-installed app (choices `install&disable` / `drop`), the same app given two verbs (`proceed` / abort). `remove=` on an installed+enabled app executes silently per config intent (deletes app data); other states skip. The resulting enabled set is written to `$DATA/cloud/recovery/apps.txt` (GENERATED, outside the repo; `make nc-capture` keeps a read-only mirror for diffs against the config). It runs only after the Nextcloud install/readiness gate (`occ status` shows `installed: true`) — deliberately, so it can read the live app set; do not move it earlier.

`scripts/install/uninstall.sh` is the exact opposite, in the same style (banner, tagged errors with problem/hint, Enter-refresh re-checks, success block). Its default run is the full teardown — three yes/no consequence confirmations, then the whole production stack and its data removed and verified gone. `--interactive` picks the scope instead — specific modules, the whole framework (every scope preselected: `RM_EDGE`/`RM_HOST`/`RM_PKGS`/`RM_USER`/`RM_TAILNET` set by `UNINSTALL_MODE=all`; data prompts still asked), or cancel — and `--granular` is reserved for the installer's module-off repair hand-off. Like the installer, every affirmation accepts only `yes`/`no` with no default, recorded as `true`/`false`. It takes the deployment apart module by module (containers down), then optionally the edge, the host services (+ the stack's ufw rules — tailnet SSH always stays), the packages, the `root` user and the tailnet membership (always last, so the session survives). It never deletes operator data without an explicit per-category confirm — the external machine NFS export is untouched, period; sshd hardening is deliberately kept (removing it would re-enable password auth). Log: `$LOG_DIR/uninstall.log`; in interactive mode the scope is preselectable via the `UNINSTALL_MODE` env. It prints the command to rebuild the stack later.

### CMD Sheet

`make help` prints the common daily recipes and `make help-more` the granular/technical ones — together they are the single source of truth for the command surface (rendered by `scripts/info/help.sh` in the same aligned colored style as the dashboard; this section used to duplicate them, a duplicate drifts). `make fetch` renders the AIO dashboard (`scripts/info/fetch.sh`: host perf, every declared module with `(not installed)` spelled out, git + the installed git hooks, units, failed units with targets, docker, tmux, backups, mail, tailnet (read from `tailscale status --json`, so self counts as up and is listed first, then the peers) — one aligned colored read); `make fetch-more` adds the repo git identity + hook state and the rest of the deep dive; `make smoke` also asserts the git hooks are installed (a missing hook means the identity/edge guards are silently gone). Raw `git`, `docker compose`, `docker exec`, `systemctl restart`, and `tar` are reserved for cases no recipe covers (one-off diagnostics the operator asked for, log/file inspection, ad-hoc reads).

**Recipe output is uniform** — every recipe speaks three lines: `info:  <what it did>` (completion), `warn:  <non-fatal issue>` and `error: <failure>` (recipe exits 1). All messages go through `scripts/lib/mklog`; usage mistakes print `error: usage: …` and exit 1. The raw tool output (occ, docker, the Mailu CLI) stays unmodified where it is the result itself.

`make git-com MSG="…"` takes a single-sentence `MSG` only — embedded newlines break the `git commit -m` quoting (`unexpected EOF` before the commit lands) and embedded double quotes break the recipe's `$(MSG)` substitution (`[: too many arguments]`). If the message needs a quote mark, wrap the whole `MSG=` in single quotes — the shell does not interpolate inside single quotes, so the embedded `"` survives intact.

### Boot and recovery

`kefo-stack.service` (`config/systemd/kefo-stack.service`; installed and enabled by `make install-config`) is the boot guarantee: a `oneshot` unit that runs `scripts/stack/stack-up.sh` after `docker.service` and `network-online.target`. It closes the one gap `restart: unless-stopped` cannot — a container stopped *cleanly* by hand (`docker stop`, `make dok-stop-*`) never comes back on its own, while `up -d` starts it again.

`scripts/stack/stack-up.sh` is the single bring-up path and never acts blindly: it derives the deployed units from the live system (`docker ps -a` plus each compose file's declared container names), so an uninstalled module is never started and never gets empty data dirs created under it. Modes: `--update` (pull + force-recreate — what `make update` runs), `--check` (start only what is missing), `--validate` (edge config only, changes nothing). In every mode the **Caddy edge goes LAST**, behind `caddy adapt` validation against the real mounts and a `caddy:rollback` image tag, and a failed edge recreate reverts to the previous image automatically. A broken edge therefore can no longer stop the rest of the stack from coming up — which is exactly what made a failed `make update` an operator lockout. The `nextcloud` unit is the one special case: when the pinned image tag and the code mounted at `data/cloud/html/version.php` disagree, the unit is brought up WITHOUT its nextcloud service and reported **blocked** (not failed, and never a gate on the edge), because a plain `up -d` would let the image entrypoint run `occ upgrade` unattended — core moves only through `make nc-core-update VERSION=x.y.z`, which bumps the tag and lets the entrypoint upgrade in the same deliberate step.

A periodic repair pass is deliberately **not installed**: boot ordering is guaranteed by `config/systemd/kefo-stack.service` + `scripts/stack/stack-up.sh`, and a supervisor that restarts containers behind the operator's back is a bigger behavioural change than that guarantee. `stack-up.sh --check` exists if the operator ever wants it (see `docs/ISSUES.md`).

## Backup & restore

- `make backup TAILDROP=<tailnet-device>` — ships every installed module to the device's `backups/` folder (tailnet-only WireGuard transfer, verified before the staging copies are deleted). No bundles are kept locally and `repo/config/` is never read or written. The mode is chosen at the prompt (`BACKUP_MODE=bundle|raw`, bundle default); the plan is then printed and a typed `yes` is required before any work:
  - **bundle** — two archives: `nextcloud-backup-<date>.tar.gz` = PostgreSQL DB (`pgdata`) + Nextcloud datadir (`cloud`); `other-backup-<date>.tar.gz` = vault, mailserver and kuma datadirs. sha256-verified after transfer.
  - **raw** — the same datadirs as plain trees, no archive: `nextcloud-<date>/` (`pgdata` + `cloud`) and `others-<date>/` (vault, mailserver, kuma). Verified with an aggregate content fingerprint (a hash of the sorted per-file sha256 manifest) since there is no tarball to hash.
  - If the datadir is external (`make nc-datadir-nfs` export — marker `$DATA/.nc-import-source`), `cloud` is sent straight from the external machine in both modes (in bundle mode the DB is copied over, the bundle built and taildropped from there); `pgdata` and the other datadirs always come from the main host.
- `make import-backups TAILDROP=<tailnet-device>` — preview: lists the bundles and raw datadirs on the device, which modules they cover, which live dirs would be overridden, which containers stop (caddy excluded), then asks what to import and requires a typed `yes` before transferring. Bundle contents and raw top-level entries must be within `{pgdata, cloud, vault, mailserver, kuma}` or the import refuses. No `DRYRUN=1` flag — preview + confirmation are built in.

Datadir interworking (`cloud` only; `pgdata` and the other datadirs are always local):

| state | `make backup` cloud source | `make import-backups` cloud destination | `make nc-datadir-nfs` |
|---|---|---|---|
| no marker | `$DATA/cloud` | `$DATA/cloud` | export → moves the datadir over NFS, writes the marker |
| marker present | the external `EX_IP:EX_MOUNT` | the external `EX_IP:EX_MOUNT` | import → moves the datadir back, removes the marker |

So a backup taken before the datadir move can be imported after it (and vice versa): the restore routes `cloud` to wherever the datadir lives now, without a `make nc-datadir-nfs` import first.
- All backups live only on the tailnet device; there is no on-host backup storage anymore. To keep a second copy, copy from the device (e.g. `ssh <device> 'rsync -a ~/backups/ <local>/'`).
- Secrets that must be preserved (`/root/.ssh/github_key`, `/etc/goose/goose.env`, `CF_API_TOKEN`...) are copies of host files; replicate them via the device copy above.

## Goose recipes

`recipes/` holds reusable Goose agent tasks — each one a `version/title/description/instructions/extensions/parameters/prompt` YAML file that tells the agent what to inspect, which tools it may use, what inputs it accepts, and what report to produce. Every recipe is **read-only**: it inspects and reports, never mutates the host, and the operator applies changes after review (the same "read-only first" discipline as `docs/DEBUG.md`). The agent's own rules stay in `docs/AGENTS.md`; these recipes point at it and at this guide rather than restating them.

The `make goose-*` front doors wrap `goose run --recipe <name>` with the repo-local `GOOSE_RECIPE_PATH` (`recipes/`), so the recipes stay versioned with the scripts and docs they operate on:

- `make goose-recipes` — list them (`goose recipe list`).
- `make goose-audit [FOCUS=…]` — full read-only audit (security/reliability/ops/docs drift).
- `make goose-review MODULE=…` — review one module (`cloud|vault|mail|monitor|edge`).
- `make goose-troubleshoot SERVICE=…` — triage a failure via `docs/DEBUG.md`.
- `make goose-check-backups [FOCUS=…]`, `make goose-check-network [FOCUS=…]` — backup and ingress/mail reviews.
- `make goose-validate-installer [TARGET=…]` — lint/review script changes (`bash -n`, no apply).
- `make goose-audit-docs [SCOPE=…]` — find doc drift/stale/duplicate.
- `make goose-deploy-plan CHANGE=…` — produce a deployment/upgrade plan.

The command list is rendered by `scripts/info/help.sh` (the same source as `make help-more`); the recipe files themselves are the source of truth for what each task does. Multi-word parameter values (e.g. `CHANGE`) hit the same make limitation as `make git-com MSG=` — pass a single token through `make`, or invoke the recipe directly: `goose run --recipe deployment-plan --params "change=upgrade the Nextcloud image"`.

## Protected host resources

**Never delete or disable any of these without explicit operator approval.** Per `docs/AGENTS.md` safety rule 1, if a task seems to require removing any of them, stop and ask.

- `/etc/systemd/system/goose.service` — goose agent systemd unit (`enabled`, `Restart=always`). Its server secret lives in `/etc/goose/goose.env` (root:root 0640, outside the repo — the unit reads it via `EnvironmentFile=`).
- Credentials are never left in loose files: the Kuma admin hash lives in its database, service secrets in `modules/*/.env` + `/etc/goose/goose.env`, and generated passwords are printed once at creation (`make kuma-passwd`, `make mail-password`). Never commit or re-print an existing secret.
- `/etc/systemd/system/ttyd.service` — ttyd web-terminal unit (`enabled`, `Restart=always`). Binds `172.22.0.1:7681` only (host bridge IP), gated by the Caddy tailnet match and the UFW INPUT allow from `172.22.0.0/16`.
- `/etc/dnsmasq.d/10-tailnet.conf` and `/etc/systemd/system/dnsmasq.service.d/override.conf` — host DNS resolver + systemd drop-in (`Restart=always`). Binds the host's Tailscale IP on port 53 only.
- `/etc/default/tailscaled` — tailscaled unit flags (`FLAGS=`, read via `EnvironmentFile=`). The installer sets `FLAGS="--encrypt-state"` **only when a TPM is present** (`/dev/tpmrm0`): on Linux the flag needs TPM, so forcing it on a TPM-less machine makes tailscaled fail to start and takes the node offline (there the console's `tsStateEncrypted` stays false — no TPM, no state encryption).
- The `caddy` container — NEVER alter, stop, or restart it without explicit operator approval; it is the ingress edge for all `$DOMAIN` routes (`make backup` / `make import-backups` exclude it).
- `$DATA_DIR/caddy_data/` — Caddy runtime data dir (LE certs under `caddy/acme/`, ACME account keys, OCSP staples) and the `CF_API_TOKEN` file used for per-vhost ACME DNS-01. The Caddy container bind-mounts this dir at `/data` so certs persist across container recreates. The `CF_API_TOKEN` file is created by the operator (see `docs/MIGRATE.md`); do not commit it.
- `$DATA_DIR/cloud/html/` and `$DATA_DIR/cloud/users/` — Nextcloud bind mounts (html root + datadirectory; both owned by uid 33 with a `.ncdata` marker in `users/`). After the datadirectory move, `cloud/users/` is an NFSv4 mount of the external machine (`/etc/fstab`, `nofail`, boot-race-hardened per the fstab options in `scripts/ops/nc-datadir-nfs.sh`) — the live datadirectory lives on the 1 TB box, and the local copy is kept at `cloud/users.local-backup` until the operator deletes it (the script won't offer the delete until the copy is verified).
- `$DATA_DIR/pgdata/` — Nextcloud PostgreSQL data dir (bind-mounted into the `postgresql` container). This directory migrates to the operator's 1 TB machine when it joins the tailnet (see "Nextcloud DB" below).
- `$DATA_DIR/talk/` — generated Talk configs: `server.conf` (signaling; 644 — the signaling container drops to uid 850 and must read it) and `turnserver.conf` (coturn; 600). Rendered by `make talk-gen` from `modules/nextcloud/talk/*.example`; contains the signaling + TURN secrets (do not commit — gitignored).
- `$DATA_DIR/download/` — file-browser drop folder, served read-only at `www.$DOMAIN/download` (Caddy bind mount `/download:ro`). Owned by `root`; anything dropped here is publicly readable.
- `$DATA_DIR/www/` — the web root for `www.$DOMAIN` and `tail.$DOMAIN` (Caddy bind mount `/srv/www:ro`). Operator-owned pages, the placeholder homepage the installer seeds once, and the GENERATED `targets.json` (`make tail-targets`). The repo ships no pages; only the tail door-list template is tracked (`config/www/tail.html`) and re-rendered into this dir on every `make render`.
- `$DATA_DIR/mailserver/` — mail platform data: `mail/` (Maildirs), `data/` (Mailu SQLite config), `dkim/` (RSA keys, mounted at `/dkim`), `filter/` (Rspamd), `certs/` (the mail.$DOMAIN pair copied from caddy_data), `redis/`, and `roundcube/` (webmail sqlite). `prep_dirs` enforces the ownership each container needs — `redis/` is `999:1000`, `roundcube/` is `33:33`, the rest `root`.
- `net` Docker network — user-defined bridge, `external: true`, subnet `172.22.0.0/16`. Reused by all inter-container services.
- SSH keys, Nextcloud data, Vaultwarden data, uploaded files — user-only (also `docs/AGENTS.md` safety rules 7 and 8).

## SSH access

SSH is restricted to the Tailscale network only — the public internet cannot reach port 22 (the installer pins `ufw default deny incoming` explicitly, because some base images ship `DEFAULT_INPUT_POLICY="ACCEPT"`, under which `ufw enable` plus the allow rules restrict nothing). Password auth is disabled; root login is key-only (`PermitRootLogin prohibit-password`); `AllowUsers root`. Config: `/etc/ssh/sshd_config.d/50-cloud-init.conf`. `root@$HOSTNAME` is the only entry point. The installer asks for the operator's public key as a required prompt in the up-front input block, before any install work, and installs it into `/root/.ssh/authorized_keys`; `phase_host` writes the sshd config only when a key is present, so a box that somehow lost its keys raises the `ssh_keys` tag and keeps password auth rather than locking the operator out. No login keypair is ever minted server-side (the one the installer does mint — `/root/.ssh/github_key` — is only for pushing to GitHub). The external machine is reached as `root@<tailnet name>`: `scripts/ops/nc-datadir-nfs.sh` connects over the tailnet with `StrictHostKeyChecking=accept-new` (key auth; `SSH_PASS` opts into `sshpass`) and fails fast with `cannot ssh to <target>` when the key is not installed there yet.

### Per-service edit pointers

When you need to know "what does X do / where do I edit Y", read the file at the path below — the docs don't re-type the contents.

- **`caddy`** (the edge) — vhosts, snippets, header policy: `modules/caddy/Caddyfile` (top-level config + `import vhosts/*.caddy`) and `modules/caddy/vhosts/*.caddy` (one per hostname: `cloud`, `kuma`, `mail`, `tail`, `talk`, `vault`, `www`). Compose + bind mounts + custom Dockerfile (Caddy built with the `caddy-dns/cloudflare` plugin for ACME DNS-01): `modules/caddy/docker-compose.yml`. Runs `network_mode: host` — see note above. Every PUBLIC vhost has its own `tls { dns cloudflare { env.CF_API_TOKEN } }` block; don't replace it with `tls internal` / `tls off` / `tls self_signed`. `tail.$DOMAIN` is the deliberate exception: it is tailnet-only and uses `tls internal` (Caddy's local CA, no LE). The container mounts the RENDERED tree (`${DATA_DIR}/rendered/caddy` → `/etc/caddy`) plus the instance web root (`${DATA_DIR}/www` → `/srv/www`); vhost edits are live config and take effect on the next `docker restart caddy` (the edge runs `admin off`, so there is no reload) — after any such restart run `make smoke`. The pre-commit hook blocks bare `respond "ok"` stubs in the app vhosts (cloud/kuma/mail/vault; www/tail are exempt by design — see the edge-guardrail gotcha). **`www.$DOMAIN`**: the homepage plus whatever pages the operator keeps in `$DATA_DIR/www` (the installer seeds one placeholder `index.html`; the `/welcome*` tellings are instance content, not repo content — the vhost's `@name path` matchers + `handle @name` pairs are what map a page name to a file); `/download` serves the public drop folder browse. **`talk.$DOMAIN`**: `/signaling/spreed` (the websocket path the Talk client opens — it appends `/spreed` to the registered `…/signaling` URL) and `/signaling/api/*` → `talk-hpb:8080`; a bare `/signaling` and everything else answer a plain `ok` by design — the vhost exists to give clients a public wss endpoint and to make Caddy issue the talk.$DOMAIN LE cert that talk-relay (coturn) reuses for TURNS on 5349. Its A record MUST stay DNS-only at Cloudflare (grey cloud — TURN speaks UDP/TCP, CF only proxies HTTP(S)); smoke asserts `/signaling/spreed` answers a websocket handshake.
- **`cloud`** — Nextcloud env, PHP-FPM pool tuning, bind mounts: `modules/nextcloud/docker-compose.yml` + `modules/nextcloud/php-fpm.d/zz-custom.conf` (pool) + `modules/nextcloud/php-conf.d/zz-opcache.ini` (opcache, bind-mounted read-only). opcache is tuned for the app file count (`memory_consumption=256`, `max_accelerated_files=20000`, `interned_strings_buffer=32`); `validate_timestamps=0`, so a code/app change is only picked up by `make dok-restart-nextcloud`. **PHP sessions are not a repo file**: the image's `/entrypoint.sh` writes `conf.d/redis-session.ini` (Redis handler + locking) from `REDIS_HOST` at every container start. Admin creds: `modules/nextcloud/.env` (gitignored — read access only via the operator). The compose file carries the Talk stack (`redis` 172.22.0.11, `talk-hpb` 172.22.0.12, `talk-relay` 172.22.0.14) — see the "Talk stack" section below. `extra_hosts` maps `mail.$DOMAIN` → 172.22.0.9 so the Mail app + NC's own SMTP see the LE-cert FQDN over the bridge. **Login by email works** — the login form accepts `admin@$DOMAIN` (NC resolves a unique email to its user); the same address is the password-reset channel (SMTP out via the local mailserver, sender `nextcloud@$DOMAIN`).
- **`cloud` rationale** — AppAPI stays disabled (no external-app support needed; keeps the attack surface small); Cloudflare Bot Fight Mode challenges non-browser clients (curl, Nextcloud desktop sync) — the workaround is a per-hostname WAF rule skip for `cloud.$DOMAIN` (see the Cloudflare-edge rationale in "Design rationale").
- **`vault`** — env, bind mount, admin token, SMTP: `modules/vaultwarden/docker-compose.yml`. Outbound email (verification/invite/notification) goes through the local mailserver as `vaultwarden@$DOMAIN` (STARTTLS 587; SMTP vars interpolated from the gitignored `modules/vaultwarden/.env` — generated by the installer `seed_stack`, mailbox created by `vaultwarden_setup`). Vaultwarden has no user CLI and signups are closed (`SIGNUPS_ALLOWED=false`), so the default account (`admin@$DOMAIN`, password stored per key in `modules/vaultwarden/.env` like the Nextcloud admin) is seeded straight into its SQLite DB by `scripts/modules/vaultwarden-user.sh` (`vaultwarden_admin` in the installer; `make vaultwarden-list-users|add-user|del-user`) — that script reproduces Bitwarden's client crypto (PBKDF2 master-key hash, the master-key-encrypted user key, and a 2048-bit RSA key pair) so a real Bitwarden client can log in; an existing account is never reset.
- **`kuma`** — image, bind mount, healthcheck: `modules/uptimekuma/docker-compose.yml`. Monitor definitions live in Kuma's SQLite (`modules/uptimekuma/seed-monitors.sql` seeds them; applied by the installer).
- **`terminal`** — `tail.$DOMAIN` is the tailnet entry point: the tailnet door list at `/` (template `config/www/tail.html`, rendered into `$DATA_DIR/www/tail.html` on every `make render`: the domain's **tailnet-only** routes — the shell plus one card per registered device session — as links from a **generated** catalogue fetched live on every visit with `cache: "no-store"`, no login, no session, no commands) and ttyd at `/ttyd` (Tailscale membership is the ONLY gate, no second credential). The catalogue is `$DATA_DIR/www/targets.json`, generated by `scripts/access/tail-targets.sh` (`make tail-targets`; `make install-config` runs it too), which reads the tail vhost's own `handle`/`@name path` pairs and the device registry (`$DATA_DIR/ttyd-devices.conf`) — nothing is hardcoded, and a public page is deliberately NOT listed. Its cert is Caddy's `tls internal` local CA (self-signed, never LE — the name is not a public ACME identifier), so browsers warn once and `make smoke` probes the routes with `curl -k`; a device only reaches them by name once the tailnet split-DNS route for `$DOMAIN` (admin console → DNS → nameservers → `$DOMAIN` → this node's `100.x`) points at this machine's dnsmasq. The whole vhost serves `Cache-Control: no-store, no-cache, must-revalidate, max-age=0` + `Pragma: no-cache` + `Expires: 0` with ETag/Last-Modified stripped — nothing on tail.$DOMAIN is cacheable. ttyd runs as a host systemd unit (not a container); interactive shells show the `root@$HOSTNAME` banner/prompt from `config/bash/banner.sh`. Binary at `/usr/local/bin/ttyd`, unit at `/etc/systemd/system/ttyd.service` (reference copy in `config/ttyd/ttyd.service`). Runs with `-b /ttyd` — base-path aware, so Caddy's `handle /ttyd*` must proxy the full path (no `handle_path` strip). No systemd sandbox (operator preference: no permission hunts). Runs as `root`, so full host control from the shell. Access control is at the network layer (Tailscale membership + Caddy `@not_tailnet`), not the unit sandbox. `make install-config` installs the binary (static 1.7.7 from upstream) and the unit; the step is idempotent. Caddy proxies to the host bridge IP `172.22.0.1:7681` with `transport http { versions 1.1 }` (ttyd only speaks HTTP/1.1); the UFW INPUT allow from `172.22.0.0/16 → 7681/tcp` is added by `make install-config`.
- **mail** — Mailu 2.0 + Roundcube: `modules/mailserver/docker-compose.yml` (mailu-front at 172.22.0.9 publishes 25/465/587/993 and terminates SMTP/IMAP TLS; mailu-imap .17, mailu-smtp .18, mailu-antispam .19, mailu-admin .20, mailu-redis .21; roundcube .10 serves webmail at cube.$DOMAIN). Mailu owns `mail.$DOMAIN` — the platform door (`modules/caddy/vhosts/mail.caddy`), the admin UI at `/admin`, and the SMTP/IMAP cert; Roundcube has its own door (`modules/caddy/vhosts/cube.caddy`) and is also proxied same-origin at `cloud.$DOMAIN/roundcube/` (`modules/caddy/vhosts/cloud.caddy`) — the `mail_roundcube` app reads the iframe's DOM, so its `externalLocation` is that URL, never `cube.$DOMAIN`. TLS is the per-vhost LE cert for mail.$DOMAIN from caddy_data, copied to `$DATA_DIR/mailserver/certs` and mounted read-only at `/certs` on mailu-front — the front's own hostname, so SNI and the cert CN match; the installer restarts `mailu-front` only when the cert bytes changed. Mailboxes live in Mailu's SQLite, managed through the `make mail-*` recipes (`flask mailu` in `mailu-admin`) — passwords are prompted or auto-generated, so nothing lands in shell history; never read `modules/mailserver/.env` or Mailu's config DB (see `docs/AGENTS.md` rule 9). Storage quotas are per-mailbox: `make mail-quota [MAIL=name@$DOMAIN] QUOTA=2G`; `0` = unlimited, and `modules/mailserver/default-quota` (tracked) is the default `make mail-gen` applies.
  **Disposable addresses**: `make mail-gen` (no args) creates a random 7-letter mailbox (e.g. `qkzfwbc@$DOMAIN`) with a random 16-char password and the default quota from `modules/mailserver/default-quota` (tracked, `100M`; `1G` when the file is absent; change with `make mail-quota QUOTA=…` and no MAIL; `0` = no limit) — credentials print once and are stored nowhere. Every field can be given explicitly instead (`make mail-gen MAIL=name PWD=… QUOTA=…`). Delete with `make mail-del MAIL=…`, which removes the account **and** its stored mail. For pure forwarding without a mailbox, `make mail-gen-alias TO=<target>` — a random 7-digit address forwarding to TO; **TO must be an external address** (same-domain targets are refused: an alias to an `@$DOMAIN` mailbox would grant that mailbox send-as for the alias); remove with `make mail-del-alias FROM=… TO=…`. `postmaster@$DOMAIN` is a real mailbox kept separate from `admin@$DOMAIN` — RFC 5321 requires postmaster to be deliverable. ### Talk stack (Nextcloud Talk HPB + TURN)

**What it is, in plain language.** Nextcloud Talk = chat + audio/video calls. Calls are WebRTC: two browsers try to talk directly (peer-to-peer). Three helpers make that reliable:
1. **Signaling** (`talk-hpb`, the official Go server) — the "switchboard". Every Talk client keeps a websocket open to it (`wss://talk.$DOMAIN/signaling/spreed`); the signaling server tells participants who else is in the call and relays small control messages. Nothing about the call *media* flows through it.
**Gotcha: the Talk websocket path is `/signaling/spreed`, not `/signaling`.** Talk's web client builds the websocket URL as `signalingServer + "/spreed"` (`getWebSocketUrl()` in the spreed bundle), so with `https://talk.$DOMAIN/signaling` registered it opens `wss://talk.$DOMAIN/signaling/spreed`. A vhost that matches only the bare `/signaling` falls through to the `respond "ok"` stub for the real handshake — the browser says "websocket connection failed", calls then run without the HPB, and the signaling server logs nothing because it never sees the request (`docker logs talk-hpb` shows only its startup block). Probe the client path with `curl --http1.1` and expect 101. A `curl --http2` probe gets 400 because Caddy's H2 layer drops `Connection`/`Upgrade` (forbidden in HTTP/2) — a curl artifact; browsers upgrade over HTTP/1.1, which `reverse_proxy` bridges. Use a literal-path `rewrite /signaling/spreed /spreed`, never a regex `uri replace`.
2. **STUN** — "what's my public IP?" so two devices behind home NATs can find each other. coturn answers this on `talk.$DOMAIN:3478`.
3. **TURN** — when direct P2P fails (mobile CGNAT, hotel/corporate WiFi, firewalled networks), coturn *relays* the media between the two sides. Credentials are minted per-session by Nextcloud from a shared secret, so it is not an open relay. Both STUN and TURN live in the same coturn container (~9 MB RAM actual).

Nextcloud tells clients about the public endpoint (`https://talk.$DOMAIN/signaling`) — the only registered signaling entry (NC 34 deprecates multiple high-performance backends; the old internal `http://172.22.0.12:8080` registration was removed 2026-08-31). The signaling server reaches Nextcloud back via its own `[backend1] urls` (`extra_hosts` maps `cloud.$DOMAIN` → 172.22.0.1), so no internal URL registration is needed. The Caddy vhost strips the `/signaling` prefix before proxying — the signaling server serves its websocket at `/spreed` and its API at `/api/v1/*`.

`modules/nextcloud/docker-compose.yml` runs four containers: `nextcloud` (.5), `redis` (.11), `talk-hpb` (.12, strukturag/nextcloud-spreed-signaling — the official Go server, no NATS needed), `talk-relay` (.14). RAM hard caps sum to 2.02 GB with the DB (1g + 128m + 256m + 128m + 512m) — the operator's 3 GB ceiling. All four carry compose healthchecks (`docker ps` shows them `healthy`); talk-relay's is a real STUN binding probe via the image's `turnutils_stunclient` — a bare TCP connect would pass while the UDP/STUN path is broken.

- **Config generation** — `make talk-gen` (idempotent): writes missing secrets into `modules/nextcloud/.env` (`SIGNALING_SECRET`, `SIGNALING_HASH_KEY`, `SIGNALING_BLOCK_KEY`, `SIGNALING_INTERNAL_SECRET`, `TURN_SECRET`, `SMTP_PASSWORD`, plus `POSTGRES_*`/`REDIS_HOST`) and renders `$DATA_DIR/talk/{server.conf,turnserver.conf}` from the committed `modules/nextcloud/talk/*.example` templates. ## Git remotes

- `origin` — the project remote: `git@github.com:$GITHUB_USER/$REPO_NAME.git` (pushes with `/root/.ssh/github_key` + `/root/.ssh/config`) or `https://github.com/…` (anonymous fetch/clone; a push there just waits for a username, since the box has no token). The installer clones over HTTPS on a fresh box but leaves an existing origin that already points at this repo alone. Read what the checkout actually uses with `git remote -v`, never assume.
- **Git identity** — all commits (this repo and `$GITHUB_USER/web-app`, history rewritten 2026-09-03) are authored `$GITHUB_USER <ID+$GITHUB_USER@users.noreply.github.com>` (repo-local `git config`), the account-noreply form GitHub maps to the account with **no verification step** — use it. **Nothing may commit or push as anything but the logged-in GitHub account** (2026-10-16): the installer writes this identity (and `user.useConfigOnly true`, so git errors instead of inventing `root@<host>`) into the checkout's repo-local `git config` at deploy time (`github_set_identity`), and the git hooks refuse any identity that is not a GitHub one — `scripts/hooks/pre-commit` blocks a commit whose effective author email is not `*@users.noreply.github.com`/`noreply@github.com`, `scripts/hooks/pre-push` blocks pushing any commit in the pushed range with such an identity. A host with no git identity silently defaults to `root@<host>`, which is how root commits entered this history; they were rewritten to the noreply identity. `--no-verify` is forbidden on every agent/operator commit and push; the wizard's own first-run push to its one-shot `temppush` remote is the sole designed exception (AGENTS.md).
- **Commit hygiene is monitored AND auto-fixed (2026-10-17)** — the two rules a commit cannot check about itself are defined once in `scripts/lib/commit-areas.sh` and used by both the checker and the rewriter: rule 26 (one change per commit, judged by AREA — `topdir/subdir`, docs/`*.md` excluded) and rule 10 (a `Revert:` line on every SIGNIFICANT commit — `Makefile`, `modules/caddy/`, each `modules/*/docker-compose.yml`, `config/{ssh,sysctl,systemd,docker,dnsmasq,cron,goose}/`, `scripts/{hooks,lib,install,render,stack,ops,access,modules}/`, or any deletion/rename). `make git-audit` (`scripts/info/git-audit.sh`, read-only) reports violations over a range (default: what a push would publish; `RANGE=origin/main` = whole published history). `make git-split` (`scripts/info/git-split.sh`) is the fixer — it replays/rebases a LOCAL range, splitting each bundle into one commit per AREA and filling each significant commit's `Revert:` line with its real parent SHA (auto rebase + auto SHA), and refuses to touch any commit already published on a remote. Two hooks call it: the **prepare-commit-msg hook auto-splits a multi-area staged change** into one commit per area (then aborts the outer commit — the work is already committed), and the **pre-push hook auto-splits the pushed range** / fills revert lines (then aborts so the operator re-runs `git push` on the rewrapped history) — the only place a GitHub-web-editor commit can be caught, since it runs no local hook — and it warn-only reports commits the remote has that this checkout lacks (`$lsha..$rsha`), because those are published and `git-split` refuses them. Splitting lives in prepare-commit-msg, not pre-commit, because pre-commit runs *before* git composes the message: a split there stamped the previous commit's message on every piece. Overrides: `GIT_SPLIT_DISABLE=1` (report/refuse instead of rewriting), `ONE_CHANGE_OVERRIDE=1` (allow a bundle commit), `HISTORY_AUDIT_OVERRIDE=1` (allow a bundle push). `make git-split ARGS=--dry-run RANGE=<a..b>` previews. The whole published history already complies (`make git-audit RANGE=origin/main` is clean), so there is no backlog to rewrite.
- **History rewrites (lessons 2026-09-02/06)** — `git filter-branch` silently drops one side of a multi-root merge DAG (verified 2026-09-02: it lost the whole $GITHUB_USER-era line) even on a pristine clone, and `git filter-repo` drops it too (verified 2026-09-03). Until 2026-09-06 this history had **two roots** ($GITHUB_USER universe merged in via `Merge branch 'main' of …/friedutch/homelab`) and a cluster of merges; it was linearized to a **single root / zero merges** via a plumbing `commit-tree` loop (see the debug-hell lesson below). Rewrites use that loop (same family as `scripts/ops/identity-rebuild.sh` (email swap) and `scripts/ops/drop-path.sh` (path purge, e.g. the 2026-09-03 `modules/nextcloud/.env` removal) — plumbing, parents-first, multi-root-safe). Verify after every run: identities uniform, tree of tip unchanged, messages + dates byte-identical, the same commit set preserved (no root added, no merge left), `git fsck` clean. **No backup tags exist** — snapshots of pre-rewrite histories were destroyed 2026-09-03 (they held the scrubbed old identities + the `.env` secret) and the old two-root objects were pruned after the 2026-09-06 linearization; the $GITHUB_USER-era commits survive only inside `main` under the noreply identity (operator's explicit choice). Never create remote tags of old histories: GitHub's Pulse/"all branches" and contributor aggregates count **every ref including tags** and map the old noreply emails to the account, so a pushed pre-rewrite tag re-exposes scrubbed identities (a batch of commits under a retired identity surfaced as a contributor) and poisons the stats.
- **Post-rewrite GitHub web index can break (lesson 2026-09-03)** — after a full-history force-push, GitHub's web git-data index can 500/404 while git stays healthy: `github.com/$GITHUB_REPO` root, `/tree/main` and `/commits` show "Page not found", and `api.github.com/repos/$GITHUB_REPO/commits` + `/git/ref/heads/main` return HTTP 500 — yet `git ls-remote` (SSH + HTTPS), `raw.githubusercontent.com`, `codeload` zips and the `issues`/`pulse`/`releases` tabs all work (A/B: `web-app` returns 200 everywhere). ## Generalization principle

Scripts and manifests stay **global** — they derive everything from the live system instead of hardcoding instance specifics (see `docs/AGENTS.md` rule 12). In practice here: the installer/nc-datadir-nfs.sh auto-detect container names, the datadirectory and DB credentials; user/group lists come from `occ`/`oc_users`, never a fixed roster; persistent recovery manifests are **generated** by `make nc-capture` into `cloud/recovery/` **outside the repo** (instance state, like `pgdata`/`backups` — never commit them; the appropriate command is `make nc-capture`, re-run to refresh). Before writing a specific user, host, IP, port, path, or container name into a script or doc, ask whether it can change — if it can, detect or prompt for it instead. Existing hardcoded leftovers should be migrated to this pattern when touched.

## Operational gotchas
- A deliberate `systemctl stop dnsmasq` takes all tailnet-side `*.$DOMAIN` resolution down. Restart with `make systemd-restart-dnsmasq`.
- **A removed tailnet node keeps its cached IP, so `tailscale ip -4` still succeeds and the installer skipped the rejoin (2026-10-16)** — after the node is deleted in the admin console the control server answers `404: node not found`, the box is offline, yet `tailscale ip -4` prints the stale address; the old `if ! tailscale ip -4` join guard therefore never fired. The guard now gates on `tailscale status --json` `.Self.Online`. A rejoin can hand the node a NEW `100.x` address; the installer's tailnet step now re-renders the split-DNS conf (`make install-dnsmasq-conf`) whenever either the `listen-address` bind or the `address=/tail.$DOMAIN/` answer no longer matches the live IP — a live bind with a stale answer resolves the door to a departed address. Tailnet `*.$DOMAIN` self-heals on the next run.
- **`systemctl restart ttyd` kills every shell it serves — including the agent that ran it (2026-09-11 19:58)** — ttyd spawns its shells (tmux sessions included) inside its own cgroup, so the restart SIGTERMs the whole group: the in-flight agent died mid-run and its tmux session vanished with it. `make install-ttyd` now refuses when the calling shell's `/proc/self/cgroup` sits inside `ttyd.service`; deploy ttyd config from SSH, or restart manually from a non-ttyd terminal.
- **`mailu-imap`/`mailu-smtp` reject plaintext auth** — Roundcube must use STARTTLS (`tls://mail.$DOMAIN:143` / `:587`). The env-derived `ROUNDCUBEMAIL_*` settings in the compose file cannot express the TLS prefix; the override lives in `modules/mailserver/roundcube-tls.inc.php` (included by the image entrypoint) and the compose `extra_hosts` maps the FQDN to the bridge IP.
- **mailu-front's `HOSTNAMES` is `mail.$DOMAIN` — the same name its cert covers** — `TLS_FLAVOR=mail` makes the front load `$DATA_DIR/mailserver/certs/{cert,key}.pem`, i.e. the mail.$DOMAIN pair copied from caddy_data, so `HOSTNAMES` must stay the name that cert covers — pointing it at a second name presents clients a CN that does not match the host they connected to. The roundcube container's `extra_hosts: mail.$DOMAIN → 172.22.0.9` plus `tls://mail.$DOMAIN` in `modules/mailserver/roundcube-tls.inc.php` rely on the same identity.
- **Mail DNS records must stay DNS-only at Cloudflare** — MX and the `mail.$DOMAIN` A record are grey-clouded; a proxied record breaks SMTP/IMAP (CF only proxies HTTP(S)).

- **The edge guardrail** — app vhosts (cloud/vault/kuma/mail) must serve their real app: the pre-commit hook (installed by the installer on every run; `make install-hooks` to re-run it manually) refuses any commit whose identity is not the logged-in GitHub account, blocks a bare `respond "ok"` in them (www and tail are exempt by design — www serves the operator's static pages, tail serves the tailnet home; a vhost another project installs is guarded by the pre-push smoke instead), runs `caddy validate` on staged `modules/caddy/` changes; the prepare-commit-msg hook auto-splits a multi-area staged change into one commit per area (rule 26 — see "Commit hygiene" above); the pre-push hook refuses a pushed range with a non-GitHub identity, auto-splits/fills revert recipes over the pushed range (rules 26/10), and runs `make smoke`. `EDGE_OVERRIDE=1` (pre-commit only) is the sole operator-approved override; the pre-push smoke has NO bypass — it runs only on a finished install (`wizard.state` `finished=true`). After any `docker restart caddy` / `make dok-recreate-caddy`, run `make smoke`.

- **The data tree lives INSIDE the repo checkout — never `chown -R` the whole tree (lesson 2026-09-22)** — `$DATA_DIR` is `$REPO_DIR/data`, so a blanket `chown -R root:root $REPO_DIR` also seizes the container-owned data dirs (33 www-data, 70 postgres, 201 caddy, 999/1000 the mail cache, 33 roundcube). Symptoms: Nextcloud answers 404 and `docker exec -u www-data nextcloud php occ` returns *"Could not open input file: occ"* (php-fpm cannot traverse its own document root); postfix answers `421 4.3.2 All server ports are busy` while its log shows `warning: cannot connect to service private/smtpd: Permission denied` (`/var/spool/postfix/private` lost its `postfix` ownership). Fix: chown only at the repo's TOP level, excluding `data/`, then restart the affected containers — Mailu re-owns its spool and `/data` on start, so recreating the mail containers clears the postfix symptom. Ownership per data dir is enforced by the installer's `prep_dirs` (Nextcloud `33`, vault `1000`, mail `0`, `mailserver/redis` `999`, roundcube `33`).
- **`config/dnsmasq/10-tailnet.conf` carries a PLACEHOLDER address, never the live one (lesson 2026-09-22)** — the tracked file says `listen-address=100.64.0.1` (a CGNAT address that is nobody's node); `make install-config` / `make install-dnsmasq-conf` rewrite that literal to the live Tailscale IPv4 at deploy time. Never copy the tracked file verbatim to `/etc/dnsmasq.d/`: dnsmasq then fail-loops with `failed to create listening socket for 100.64.0.1: Cannot assign requested address` and takes tailnet DNS — and with it `tail.$DOMAIN` — down. The placeholder is a fixed literal on purpose (it used to come from a `TAILNET_SUBNET` instance value, which meant the tracked file contained a real address).
- **A module that is not installed has no route — never report it as "tailnet-only" (lesson 2026-09-22)** — `vault.$DOMAIN` answered 502 and the closing report called the vhost "tailnet-only"; the truth was that the `vault` module simply was not in `enabled_modules` in `wizard.state`. Grep-able symptom: a 502 with no container. Fix the report, not the system: `make fetch` (`vault (not installed)`), `make fetch-more` (`routes` + `!dead` rows) and `make smoke` (buffered into the end "Not installed / ignored" section) all carry the right words now. See "Module state vs route exposure".
- **The web root is INSTANCE DATA and must NOT be mounted inside the rendered config mount (2026-09-22; corrected 2026-09-25)** — `modules/caddy/docker-compose.yml` mounts `${DATA_DIR}/www:/srv/www:ro` (a plain sibling path) alongside `${DATA_DIR}/rendered/caddy:/etc/caddy:ro`. It used to be nested at `/etc/caddy/www`, which is a hard failure on current Docker/runc: mounting the parent read-only first makes runc `mkdir` the nested mountpoint *inside* that read-only filesystem and the container dies at create time —
  `error mounting ".../data/www" to rootfs at "/etc/caddy/www": ... mkdirat .../merged/etc/caddy/www: read-only file system`
  so Caddy stays `Created`, never listens, and every ACME cert stays unissued (one bug, seven error tags on the 2026-09-25 fresh install). Pre-creating the dir in the image does not help — only de-nesting does. Symptom if the mount is missing entirely: every static page falls through to the `respond "ok"` stub.
- **An uninstalled module's own state is invisible to the edge (2026-09-22)** — `stack-up.sh` derives its unit list from the live containers, and the tail catalogue only lists routes that exist, so a module removed from `enabled_modules` neither starts nor appears anywhere. That is the designed behaviour; the only visible trace is the dead vhost line `make fetch-more` prints.
- **The module writer used a bad substitution → empty module record → muted smoke (2026-10-04)** — the installer tested `[ "${MOD_${m^^}:-true}" = "true" ]`; nested `${m^^}` inside a variable name is not valid bash, so the test errored and no module was ever recorded — a fresh install then ran with an empty record, `make fetch` reported every module "not installed", and `make smoke` muted every module section and kept real failures OUT of its exit code. Grep-able tell: `make fetch` shows `modules … (not installed)` while all containers are up. Fix: `local _mod="MOD_${m^^}"; [ "${!_mod:-true}" = "true" ]` (build the name first, indirect it — same pit as the documented bash-array `${RM_MOD_${k^^}}` bug).
- **Mailbox gaps are silent, so `mailbox_add` verifies against Mailu's own export (2026-10-15, Mailu-era 2026-10-19)** — `flask mailu user` and `config-update` write to the admin container's SQLite with no useful exit signal, so a check based on a CLI row format (the old docker-mailserver `setup email list` regex) can report a mailbox missing while it exists. `mailbox_exists` now matches `localpart@domain` against `flask mailu config-export -j` with `jq`, `mailbox_add` logs the CLI output and re-verifies for 90 s, and `mail_wait_ready` probes a real command (`config-export -j`) — never `flask mailu --help`, which trips a Flask 2.2 assertion in Mailu 2.0. Grep-able tells: a reported-missing mailbox that `make mail-card` finds, or an admin container that answers `docker exec true` while every write fails (recreate it; the config store is not writable).
- **A push is blocked until the install is `finished` (2026-10-15)** — `make smoke` refuses to run unless `data/wizard.state` records `finished=true`, and the pre-push hook (installed by the installer, or `make install-hooks` on any other clone) runs `make smoke` with NO bypass. Grep-able symptom: `pre-push: vhost smoke test FAILED` while the edge is actually serving, or `smoke: wizard.state is not finished ('absent')`. Cause: a host that never completed an install (or a fresh clone) has no `finished` checkpoint, and nothing but the installer may write it. Takeaway: finish an install before pushing from a host that has the hook installed; installing the hook on a dev host that is not a finished install makes every push fail by design. The pre-commit side keeps its operator override `EDGE_OVERRIDE=1`; the pre-push side has none.
- **The edge must mount the RENDERED tree, not the tracked one (lesson 2026-09-22)** — `modules/caddy/docker-compose.yml` mounts `${DATA_DIR}/rendered/caddy`. Point it at `./` (the tracked dir) and Caddy does not error: the skeleton's site blocks literally say `https://www.{{DOMAIN}}`, so Caddy starts, binds 80/443, passes its `caddy version` healthcheck and serves **nothing** — every probe returns `000`, `curl -sk` gives no reply and `docker logs caddy` is empty. Symptom to grep for: edge healthy + every vhost `000`. Fix: `make render` then `make dok-recreate-caddy`; `scripts/stack/stack-up.sh` renders first in every mode and `--validate` catches a config that will not load.
- **Every log the project writes lives in `$LOG_DIR` (`$DATA_DIR/logs`, repo-relative — no `$GITHUB_USER` namespace), one logrotate rule, nothing chronicle-style (2026-09-22)** — `wizard.log`, `uninstall.log` and any module log share the directory; the installer state is `$DATA_DIR/wizard.state` (mode 0600). Docker logging is capped in `config/docker/daemon.json` (json-file, 10m x3); the systemd dirs contain only `kefo-stack.service` and `tmux-main.service`. The pre-2026-09-22 paths (`/var/log/kefoCloud-install.log`, `/var/log/homelab-install.log`) are relocated by the installer on first run — never deleted.
- **`talk-hpb` needs `init: true` (2026-09-22)** — `strukturag/nextcloud-spreed-signaling` spawns short-lived `timeout` children and never reaps them: 81 zombies in ~40 minutes of uptime, which is PID-table exhaustion over weeks. `init: true` (tini as PID 1) fixed it; the count is 0. A `diagnose` pass that shows `N zombies` in `make fetch-more` is how it surfaced.
- **A setup failure must be HEALED, not probed (lesson 2026-10-15)** — `nextcloud_setup` failed with `nextcloud not installed/ready after 30 min` on a Nextcloud that was `installed: true` and answered HTTPS in under a second, and the tag could never clear. Two causes: (a) the readiness probe's `occ status` raced the `containers_up` force-recreate (`make dok-recreate-nextcloud` restarts nextcloud + redis; occ fails on a cold cache for the first ~10-30 s, so the FIRST probe ran inside a 0.48 s window on a warm box and never mattered until the recreate moved it) — the readiness loop waits 30 min and the occ-wiring checks are short (12x1 s each) and re-applied in-run before any tag is raised, and the occ-wiring step no longer raises a tag at all — it re-applies the idempotent wiring a few times and logs, never failing (a wiring race is TIME, not a fault); (b) `recheck nextcloud_setup` can only inspect occ config, and that config is written by `nextcloud_setup` itself, so with `MOD_MAIL=true` the arm answered false forever. `resolve_errors` now re-runs the idempotent setup step for `nextcloud_setup` / `vaultwarden_setup` / `dkim_setup` before rechecking. Grep-able tell: an "Unexpected errors" tag that survives a re-check while the service underneath is demonstrably healthy. Also fixed the same tag's `mail.$DOMAIN` check, which used the wrong `MOD_MAIL` fallback.
- **A crashed installer reports stale error tags, and a missing `$LOG_DIR` fakes a `render` failure (2026-09-25)** — a run died in `prep_dirs` with `ROOT: unbound variable` (the installer named the checkout root `$REPO` while its own `$ROOT/data/...` paths kept the repo-wide `$ROOT`; `set -u` then exits, and the `trap summary EXIT` re-prints the persisted `ERR_TAGS` from `$DATA_DIR/wizard.state` — so tags from earlier in the run appear as if current). The `render` tag next to it was false: `write_instance_conf` logs and renders into `$LOG` **before** `phase_host` created `$LOG_DIR`, so the `>>"$LOG"` redirection failed, the renderer never ran, `|| fail render` fired and two log lines vanished. Tell: when a tagged error looks unrelated, grep `wizard.log` for the output the step should have produced (and for its first lines) — the step's output being *absent* is the evidence, not its presence. `ensure_runtime_dirs()` now creates `$LOG_DIR` and tightens `$DATA` (0600 state) before anything redirects into them.
- **`ssh … | grep -q` is always false under `set -o pipefail` when ssh exits non-zero (2026-09-25)** — `ssh -T git@github.com` prints "successfully authenticated" but exits **1** (no shell access), so the installer's GitHub key test reported "not authorized" on a key that worked; the fix is to capture the output first and grep the variable. Any `cmd | grep -q` line in these scripts inherits the trap: pipefail makes the pipeline's status the *left* command's.
- **`make fetch` reported two permanently-failed host units (2026-10-16)** — `openipmi.service` (`LSB: OpenIPMI Driver init script`, fails with `Starting ipmi drivers ipmi failed!` — the box has no IPMI hardware) and `systemd-networkd-wait-online.service` (`Timeout occurred while waiting for network connectivity` after 2 min — networkd is active but `networkctl` shows every link `unmanaged`, so no interface can ever satisfy it). Both are distro units, not repo services: the installer's `disable_benign_failed_units()` (called from the Host Services task) disables exactly these two and clears their failed state, so `systemctl --failed` (`make fetch`) stays clean and boot skips the dead 2-min wait — re-enable manually with `systemctl enable …`. It touches only these two known units (never a blanket `reset-failed`, which would hide a real one); distro- or hardware-dependent units like these are the only ones it manages.
- **A checklist write that does not return the cursor to column 0 concatenates rows (debug hell 2026-10-16)** — symptom: late in the install two rows mash into one line, e.g. `Repository Managementent[   $    ] [EXEC] Repository Management[…][DONE] DNS Records`, only after the block has scrolled. Root cause: `_task_update`/`_note` end each row with a bare `\n`, which returns to column 0 **only while the tty does NL→CRNL (ONLCR)**; anything that runs the terminal without ONLCR leaves the cursor mid-line and every later row is appended after the previous (a *wrapped* note miscounts `_TAIL` the same way — one logical line counted as one row while it occupies two). Fix: every block/note write now opens with an explicit CR, `_note` counts **physical** rows (width from `stty size`, ANSI stripped), and `_tasks_draw` re-asserts `stty onlcr icrnl` before drawing. Recognise it by a `[EXEC]`/`[DONE]` row that begins mid-line rather than at column 0. Repro without a real install: `sed -n` the block out of the installer, source it under `script -qec` with `stty -onlcr`.

- **notify_push v1.4 is not a zero-config container (2026-10-18)** — the image is from scratch and needs `DATABASE_URL`, `DATABASE_PREFIX` and `REDIS_URL` (without them it exits with `No database server is configured` and crash-loops), plus `NEXTCLOUD_URL` set to the PUBLIC `https://cloud.$DOMAIN` (the PHP-FPM upstream makes `notify_push:setup`'s trusted-proxy test fail). Caddy must trust the push container's forwarded header for the same test: `php_fastcgi` carries `trusted_proxies 172.22.0.16/32`. Do not add a healthcheck — the scratch image has no shell/curl, so any probe reports `unhealthy` forever; `occ notify_push:self-test` is the real check.
- **Declaration-detection probes must not count repo files (2026-10-18)** — `write_state()` counted the module's compose file existing in the checkout as "detected", which is always true for every declared module, so `declared != detected` warned on every run; leftover data dirs/rendered vhosts from an uninstall confirmed it too. Confirmation is now only "the module's container is running"; data/vhost are still printed as leftovers.
