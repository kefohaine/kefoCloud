## Intended

Behaviours that look like bugs but are deliberate. Do not fix; the rationale is the answer.

### `shell.fxmq.net` is unresolvable from the public internet
Looks like: DNS lookup fails for `shell.fxmq.net` outside Tailscale, *or* a `curl` against `https://shell.fxmq.net/` (any path) from a non-tailnet source times out, returns 403, or connection-refuses — including from the VPS host itself if the host isn't on the tailnet resolver. Reality: this is the only access control — see the access model table in `README.md`. The Caddy `@not_tailnet` matcher requires the `fxmq.net` container to be on the host network namespace (`network_mode: host`) so Caddy sees the real source IP — Docker DNAT through the bridge would rewrite it to `172.22.0.1` and break the matcher. **A failed curl is `@not_tailnet` working, not a service outage** — verify from a tailnet device or by SSH'ing in and curling from a tailnet-joined source.

### Cloudflare Bot Fight Mode blocks `curl` against `cloud.fxmq.net`
Looks like: Cloudflare rejects `curl`/scripts hitting `cloud.fxmq.net` with a 403 / challenge. Reality: terminal traffic cannot solve the Browser Integrity Check. The intended fix is a per-hostname WAF rule skip on `cloud.fxmq.net` (desktop sync is bot-challenged otherwise); the goal is to keep Cloudflare's full protection on everywhere else.

### Talk recording + SIP backends not configured
Looks like: setup-check warnings "No recording backend configured" / "No SIP backend configured". Reality: a single-operator Talk instance has no recording server and no SIP trunk — the warnings are expected and not bugs. Revisit only if calls need recording or PSTN dial-in.

### Talk HPB "missing features: changed-users"
Looks like: Talk warns the signaling server doesn't support all features (`changed-users`). Reality: the official `strukturag/nextcloud-spreed-signaling:latest` image is 2.1.1 (built 2026-03-12, verified up to date) and predates that Talk feature — no newer image exists on Docker Hub. Do not chase this warning; it clears only when upstream ships a newer signaling server.

### AppAPI disabled (no external apps)
Looks like: "AppAPI default deploy daemon is not set" would appear if `app_api` were enabled. Reality: `occ app:disable app_api` was run 2026-08-31 — no External Apps (Ex-Apps) are used, so the framework is off and the warning gone. Re-enable (`occ app:enable app_api`) if ExApps are ever wanted.

## Lessons learned

Facts that were non-obvious and only surfaced by grepping the repo or hitting an error — kept so a future agent doesn't have to re-discover them. See `docs/GUIDE.md` § Operational gotchas for the operational checklist.
- **NC mail connects ANONYMOUSLY until `mail_smtpauth` is set** — NC's Mailer only passes the username/password to Symfony when the `mail_smtpauth` system config is true (`lib/private/Mail/Mailer.php`); host/port/tls/LOGIN/credentials alone are not enough, so every send 554s at RCPT with "Client host rejected: Access denied" (the credentials themselves pass a manual SMTP AUTH). The mail log shows `Anonymous TLS` + `ehlo=2 starttls=1 mail=1 rcpt=0/1` (no AUTH command). Fix: `occ config:system:set mail_smtpauth --value true` (now in install.sh's nextcloud_setup). Grep-able: `mail_smtpauth`, "Client host rejected", "Anonymous TLS".
- **The CF token file is env-format, not a bare token** — `caddy_data/CF_API_TOKEN` contains `CF_API_TOKEN=<value>` (a 53-char token, `CF_` prefix + `=` at byte 12) with a trailing newline; using the raw file content as a Bearer token fails with CF error 6111 "Invalid format for Authorization header". Extract with `sed 's/^CF_API_TOKEN=//' | tr -d '\r\n'`. Caddy's ACME works because the compose mounts the file where the Caddyfile's `env.CF_API_TOKEN` resolves the var form. Grep-able: `6111`, `CF_API_TOKEN=`.
- **DKIM record published via the CF API (2026-09-01)** — Rspamd signs (`DKIM_SIGNED{fxmq.net:s=mail;}`), the `mail._domainkey` TXT matches the signing key, and a stale `h=sha256` DKIM record from an earlier attempt was found and deleted; verify against the authoritative NS (`dig @sandy.ns.cloudflare.com`) — resolvers lag until the old TTL expires.
- **install.sh is now fully automatic for mail** — `mail_smtpauth=true` (NC authenticates — the "Client host rejected" saga), `mail_smtpport` as a string (UI TypeError), trusted_proxies array, repair + `db:add-missing-*` (setup-check warnings), the updater-backup dir (cleanup-job warning), the recovery manifests (users/groups/quotas/apps), and the **DKIM key generated + TXT published via the Cloudflare API** (`mail._domainkey`); the only remaining external-delivery step is the operator's provider-side PTR. (2026-09-01)
- **NC 34 settings-UI mail form throws a TypeError** (`MailSettingsController::setMailSettings(): Argument #7 ($mail_smtpport) must be of type string, int given`) — the controller declares `string $mail_smtpport`, and storing the port as an INTEGER (`occ config:system:set mail_smtpport --value 587 --type integer`) makes the UI echo an int back → the save fails with the TypeError. Store the port as a plain string (no `--type integer`) and the UI save works. Related UI traps: the form writes whatever it posts — an untouched encryption dropdown or credential fields save as EMPTY (clobbering the occ-set `mail_smtpsecure`/`mail_smtpname`), and the masked password field posts the literal `********` placeholder as the real password. In 34.0.3 the mail settings UI is not trustworthy — configure via occ/`make nc-config-set` and only use the UI's "Send email" test on a freshly loaded page. Grep-able: `mail_smtpport`, "must be of type string", `********`.
- **NC primary object store keys blobs by `urn:oid:<fileid>`** — never by path. Migrating local files to a primary S3 store = upload each local file to the key `urn:oid:<filecache fileid>` (NOT a path-based tree copy — a path copy produces 403/404 reads and empty listings) AND move the filecache rows to the `object::*` storages (`UPDATE oc_filecache SET storage=<object::numeric_id> ...`; `files:scan` does NOT migrate rows — without the move, `Cache` lookups work but the user view returns 0 entries). The datadirectory (appdata) is object-backed too under primary store (`object::store:amazon::nextcloud`), so appdata blobs must be uploaded as well. Verify with a php probe through `\OC\Files\Filesystem::getView()` + `file_get_contents` and check the S3 access log for the GET. Grep-able: `urn:oid`, `object::store:amazon::nextcloud`, "Could not get object".
- **Garage publishes NO static binaries** — the official artifact is the Docker image `dxflrs/garage` (distroless: no entrypoint and no `sh`, binary at `/garage` — invoke `/garage server -c ...` explicitly). v2 config gotchas: nested `s3_api = { api_bind_addr = ..., s3_region = "garage" }` + `admin = { api_addr, admin_token }` + `replication_factor = 1` — the docs' flat keys (`api_bind_addr`/`s3_region`) fail with "missing field s3_api", and a wrong field inside `s3_api` (e.g. `api_addr`) is silently ignored so the S3 listener never binds. Grep-able: `s3_api`, `api_bind_addr`, `replication_factor`.
- **Garage CLI quirks** — `key delete` requires `--yes` (silently aborts without it); `key info` REDACTS the secret (capture it at `key create`); a name pattern matching multiple keys errors "2 matching keys" (delete by full ID). Grep-able: `key delete`, "2 matching keys", `Secret key:`.
- **mc (minio client) against garage needs the region in the alias** — without `"region":"garage"` in the alias config, requests 400 with "unexpected scope: '20260831/us-east-1/s3/aws4_request', expected: '20260831/garage/s3/aws4_request'" (the bucket-location probe fails; some ops still pass). Grep-able: `unexpected scope`, `aws4_request`.
- **`occ maintenance:mode --on` blocks app commands** — `files:scan` fails with "There are no commands defined in the files namespace" while maintenance mode is on; turn it off before scanning (and remember to clear a stuck mode at the start of any re-runnable migration). Grep-able: `maintenance mode, no apps are loaded`.
- **`require config.php` returns 1, not the array** — NC's config.php has no `return`; when editing it via `php -r`, use `require $f; $c = $CONFIG;`. Grep-able: "Cannot use a scalar value as an array".
- **`\OC_Util::setupFS($uid)` roots the view at the user's `files/` dir** — a php probe's paths are relative to `files/` ("Reasons.pdf", not "files/Reasons.pdf"); probing with the `files/` prefix silently returns 0 bytes / NULL info. Grep-able: `setupFS`, `view root`.
- **Makefile `$(USER)` is polluted by the shell environment — always `op`** — GNU make imports exported env vars as variables, so a recipe guard like `[ -n "$(USER)" ]` NEVER fires: `make mail-del` without `MAIL=` silently operated on the wrong address (and `$(MAIL)` = `/var/mail/op`). Fix: guard with `[ "$(origin USER)" = "command line" ]`. Related trap: each recipe line is its own `bash -eu -c` process, so `exit 0` inside a guard does NOT stop the recipe — it just ends that line's shell and make runs the next line (a "not found" guard followed by `sudo rm -rf` deleted nothing but printed the wrong success message). Put the guard and the destructive command in the SAME recipe line (or `exit 1`).
- **NC "Email could not be sent" is usually the SMTP host, not the password/mailbox** — the 2026-08-31 failure: welcome mails to new users + the admin test mail both failed with `Symfony ... TransportException: Peer certificate CN='mail.fxmq.net' did not match expected CN='172.22.0.9'`. `mail_smtphost` was the bridge IP; Symfony verifies the LE cert CN and the IP can't match. Fix: `occ config:system:set mail_smtphost --value mail.fxmq.net` (the container's `extra_hosts` maps the FQDN to 172.22.0.9, so SNI + CN match — same pattern as roundcube). Grep-able: `mail_smtphost`, `Peer certificate CN did not match`, `stream_socket_enable_crypto`. The mailbox `nextcloud@fxmq.net` existed and was never the problem (symptom in `/data/nextcloud.log`, not the mail log).
- **NC "Email could not be sent" can also be `mail_smtpsecure=ssl` on port 587** — `ssl` means implicit TLS (port 465); on 587 Symfony's client dies after the banner with a generic "Email could not be sent" and ZERO postfix auth attempts (the 2026-08-31 15:15 test-mail failures). Fix: `occ config:system:set mail_smtpsecure --value tls` (STARTTLS) + `mail_smtpauthtype --value LOGIN`. Grep-able: `mail_smtpsecure`, `Email could not be sent`.
- **Caddy's `header` directive appends to upstream values — it does NOT replace them** — apps that already send X-Frame-Options / X-Content-Type-Options / Referrer-Policy (Nextcloud, Vaultwarden, Kuma) ended up with duplicate headers and a conflicting Referrer-Policy (NC's `no-referrer` + Caddy's value) behind the reverse proxy; scan.nextcloud.com flags the duplicates. Two gotchas: (1) `header Field Value` ADDS to whatever the upstream already sent; (2) a delete+set pair for the SAME field in one header block results in the field being deleted (delete wins). The working fix: `header_down -X-Frame-Options` (ONE field per `header_down` line — a multi-field line is silently truncated to the first field by the Caddyfile adapter) inside each app's `reverse_proxy`/`php_fastcgi` block strips the upstream copies, then the site-level `header` set yields exactly one value per field. Grep-able: `security_headers`, `header_down`, duplicate `x-frame-options`.
- **NC updates go through the compose image tag, not the web updater** — see `docs/GUIDE.md` operational gotchas (Docker image filesystem; the updater app can't apply or survive recreates).
- **NC 34's background-jobs mode lives in the APP config, not the system config** — `occ background:cron` prints "Set mode for background jobs to 'cron'" but `occ config:system:get backgroundjobs_mode` returns nothing (exit 1). Verify with `occ config:app:get core backgroundjobs_mode` → `cron`. Grep-able: `backgroundjobs_mode`, `background:cron`.
- **The Nextcloud image entrypoint re-applies `TRUSTED_PROXIES` at every boot, writing the whole comma list into `trusted_proxies` index 0** — NC 34's setup check then reports trusted_proxies "should be an array" and the brute-force throttle sees the Cloudflare edge IP (104.23.x) as the client. Removing the env var from the compose (recreate, not restart — restart keeps the old env) and setting the array via `occ config:system:set trusted_proxies <i> --value <cidr>` per entry is the fix that survives boots. Grep-able: `TRUSTED_PROXIES`, `trusted_proxies`, `104.23`.
- **Vhost edits in the worktree are LIVE config — Caddy serves them without any build/reload ceremony.** `services/fxmq.net/` is bind-mounted into the container at `/etc/caddy` (`ro`), so the running proxy always reflects the working-tree vhost files (plus a `docker restart fxmq.net` when Caddy needs to re-read them). An uncommitted vhost edit — or a committed one the operator never verified — takes every affected vhost down the moment the container restarts. The `0b9fe02` "decommission to ok stubs" commit went live like this and the operator had to declare it a critical emergency. Always: (1) treat vhost changes as production config regardless of git state, (2) smoke every vhost after any restart, (3) never commit an edge-wide routing change without operator sign-off. The stub files were backed up to `/tmp/vhost-stubs-20260828/` before the restore.
- **Recreating the roundcube container leaves a "logged in but IMAP-broken" session** — the image stores sessions in the sqlite DB (`session_storage = 'db'`), so after a `--force-recreate` (e.g. the mail→mailserver rename) the old session survives and the UI renders authenticated, but the IMAP connection died with the container and roundcube reconnects with an empty session password → mail tab shows "Connection to IMAP server failed. Server Error: Empty password" and an empty list, with ZERO dovecot auth attempts in the logs (the tell: no `imap-login` lines from the roundcube IP after the recreate). Fix: log out and log in again (or clear the roundcube cookie); the IMAP stack itself is fine (dovecot logs `Login: user=... method=PLAIN ... TLS` on healthy logins, cert at `/caddy/.../mail.fxmq.net.crt` is present).
- **Docker embedded DNS shadows public hostnames with container hostnames** — the mailserver container has `hostname: mail.fxmq.net`, so inside ANY `net`-network container (kuma, a throwaway `docker run`) `mail.fxmq.net` resolves to 172.22.0.9 instead of the public IP. SMTP/IMAP clients on the bridge benefit (roundcube's `extra_hosts` is redundant), but an HTTP(S) check from a container against `mail.fxmq.net` hits 172.22.0.9:443 → ECONNREFUSED because Caddy owns :443 on the HOST. Symptom: kuma monitor "mail.fxmq.net" DOWN while the website works (monitor URL `https://mail.fxmq.net` → resolved 172.22.0.9:443). Fix: monitor `http://172.22.0.10:80/` (roundcube on the bridge) or TCP on 172.22.0.9:993/25 — never the hostname for HTTPS from a container. Verify with `docker exec uptimekuma node -e "require('net').connect(80,'172.22.0.10',()=>process.exit(0)).on('error',()=>process.exit(1))"`.

- **A vhost with no `tls` directive does not "use ACME by default" — it picks up any loaded cert that matches the SNI.** The `mc.homelab.com` vhost had no `tls` directive, intended to fall through to ACME, but Caddy served the wildcard `*.homelab.com` CF Origin cert as a SNI fallback. The automation policy never had a reason to fire because the wildcard cert was always available. Symptom: `mc.homelab.com` returned 200 OK from the first hit, but the cert issuer was `CloudFlare Origin CA`, not `Let's Encrypt`. To confirm ACME is actually firing, check the issuer on a fresh TLS handshake (`echo | openssl s_client -connect mc.homelab.com:443 -servername mc.homelab.com | openssl x509 -noout -issuer`) — not the HTTP response code.
- **Caddy stock `caddy:2.x` images do not include the `caddy-dns/cloudflare` plugin.** Symptom: `module not registered: dns.providers.cloudflare` on container startup. Fix: build a custom image with `xcaddy build --with github.com/caddy-dns/cloudflare@<commit>` (see `services/fxmq.net/Dockerfile`). The `caddy` Docker Hub image only includes the core modules plus the conventional ACME issuer.
- **The `caddy-dns/cloudflare` v0.2.3 tagged release rejects the new 53-char CF API tokens** with a confusing "API token ... appears invalid; ensure it's correctly entered and not wrapped in braces nor quotes" error. The provider's regex is `^[A-Za-z0-9_-]{35,50}$` (40–50 character token range) — the new CF tokens are 53 chars. PR #123 on `caddy-dns/cloudflare` relaxed the regex; pull from `a8737d0` (master) until a tagged release lands.
- **`caddy:2.11.4` requires Go ≥ 1.25.1 to build.** The `golang:1.25-bookworm` image satisfies this. Older builder images (`golang:1.24-bookworm` and earlier) fail with `go: github.com/caddyserver/caddy/v2@v2.11.4 requires go >= 1.25.1`. If you bump Caddy later, check the `go` directive in `caddy/v2/go.mod` and bump the builder image accordingly.
- **The cert's issuer is the only reliable indicator of which path it took.** When debugging Caddy TLS, `curl -sk` returning 200 means "the listener responded" — not "the right cert was served." Always check `openssl x509 -noout -issuer` on a fresh `-no-keepalive` request. The CF Origin CA cert, the LE cert, and the staging LE cert all return 200 to `curl`; only the issuer tells you which path served it.
- **The `mc.homelab.com` vhost is the only one that *had* to use DNS-01** — the game ports (25565 Java, 19132 Bedrock) are published directly on the VPS and bypass the CF proxy at the port layer, so `mc.homelab.com` is DNS-only at CF. Turning the CF proxy on would break the game ports. The other vhosts use DNS-01 now too for consistency, but HTTP-01 would have worked for them.
- **`network_mode: host` is required for `@not_tailnet` to work** — Caddy needs to see the real client source IP, and Docker DNAT on the bridge network rewrites every packet to `172.22.0.1` (the gateway). Without `network_mode: host`, the `100.64.0.0/10` matcher matches nothing and every tailnet request gets 403. This is set in `services/fxmq.net/docker-compose.yml` — do not "fix" it by removing the `hosts: network_mode`.
- **The CF API token file at `$(REPO)/caddy_data/CF_API_TOKEN` is the only thing the operator needs to migrate to a new VPS** — Caddy renews certs from the token, so transferring it skips the 0–90-day issuance window. The token file is not in `bundle-secrets` (Caddy regenerates the certs from the token on the new host, so off-VPS cert copies aren't needed). The `bundle-secrets` recipe was reduced to drop the retired `$(REPO)/certs` reference.
- **The Caddy data dir lives at `$(REPO)/caddy_data/`, OUTSIDE the repo, and `git status` will never mention it** — surprising because every other secret in this project (`services/nextcloud/.env`, the Vaultwarden admin token, etc.) sits inside `services/<ctn>/.env` and shows up under `git status` as a tracked-or-ignored file. Caddy's is the opposite: it lives one directory above the project root, is never tracked, never ignored, and is invisible to `git` until you specifically `ls /var/www/custom/projects/homelab/`. A grep for `CF_API_TOKEN` across `repo/services/` returns nothing — the env wiring happens entirely via the `env_file:` directive in `services/fxmq.net/docker-compose.yml`.
- **`docker compose env_file:` reads the file as the UID running `make dok-recreate-fxmq.net`, NOT as the UID inside the container** — surprising because most Docker env handling happens at container start.
