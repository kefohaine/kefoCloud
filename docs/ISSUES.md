## Intended

Behaviours that look like bugs but are deliberate. Do not fix; the rationale is the answer.

### `shell.fxmq.net` is unresolvable from the public internet
Looks like: DNS lookup fails for `shell.fxmq.net` outside Tailscale, *or* a `curl` against `https://shell.fxmq.net/` (any path) from a non-tailnet source times out, returns 403, or connection-refuses — including from the VPS host itself if the host isn't on the tailnet resolver. Reality: this is the only access control — see the access model table in `README.md`. The Caddy `@not_tailnet` matcher requires the `fxmq.net` container to be on the host network namespace (`network_mode: host`) so Caddy sees the real source IP — Docker DNAT through the bridge would rewrite it to `172.22.0.1` and break the matcher. **A failed curl is `@not_tailnet` working, not a service outage** — verify from a tailnet device or by SSH'ing in and curling from a tailnet-joined source.

### Cloudflare Bot Fight Mode blocks `curl` against `cloud.fxmq.net`
Looks like: Cloudflare rejects `curl`/scripts hitting `cloud.fxmq.net` with a 403 / challenge. Reality: terminal traffic cannot solve the Browser Integrity Check. The intended fix is a per-hostname WAF rule skip on `cloud.fxmq.net` (desktop sync is bot-challenged otherwise); the goal is to keep Cloudflare's full protection on everywhere else.

## Lessons learned

Facts that were non-obvious and only surfaced by grepping the repo or hitting an error — kept so a future agent doesn't have to re-discover them. See `docs/GUIDE.md` § Operational gotchas for the operational checklist.
- **Vhost edits in the worktree are LIVE config — Caddy serves them without any build/reload ceremony.** `services/fxmq.net/` is bind-mounted into the container at `/etc/caddy` (`ro`), so the running proxy always reflects the working-tree vhost files (plus a `docker restart fxmq.net` when Caddy needs to re-read them). An uncommitted vhost edit — or a committed one the operator never verified — takes every affected vhost down the moment the container restarts. The `0b9fe02` "decommission to ok stubs" commit went live like this and the operator had to declare it a critical emergency. Always: (1) treat vhost changes as production config regardless of git state, (2) smoke every vhost after any restart, (3) never commit an edge-wide routing change without operator sign-off. The stub files were backed up to `/tmp/vhost-stubs-20260828/` before the restore.
- **Recreating the roundcube container leaves a "logged in but IMAP-broken" session** — the image stores sessions in the sqlite DB (`session_storage = 'db'`), so after a `--force-recreate` (e.g. the mail→mailserver rename) the old session survives and the UI renders authenticated, but the IMAP connection died with the container and roundcube reconnects with an empty session password → mail tab shows "Connection to IMAP server failed. Server Error: Empty password" and an empty list, with ZERO dovecot auth attempts in the logs (the tell: no `imap-login` lines from the roundcube IP after the recreate). Fix: log out and log in again (or clear the roundcube cookie); the IMAP stack itself is fine (dovecot logs `Login: user=... method=PLAIN ... TLS` on healthy logins, cert at `/caddy/.../mail.fxmq.net.crt` is present).
- **Docker embedded DNS shadows public hostnames with container hostnames** — the mailserver container has `hostname: mail.fxmq.net`, so inside ANY `net`-network container (kuma, a throwaway `docker run`) `mail.fxmq.net` resolves to 172.22.0.9 instead of the public IP.
